Overview

Verdant Reach is a Game Boy Color–style monster collector: Pokémon Crystal's structure with a set of deliberately updated mechanics, in which every creature is a real plant. It runs in the browser, renders a fixed 160×144 screen into one <canvas>, and ships with zero runtime dependencies. This section is the map you need before anything else: what the project is, why it is built the way it is, where things live, how to run it, and the game's own words for familiar ideas.

What the project is

The scope is the whole game: the Prologue through Chapter 11 (the Council, the ending and the credits) plus a post-game. The live site is https://minormending.github.io/verdant-reach/, and it deploys automatically on every push to main. The workflow (pages.yml) has three jobs: build runs the tests, the release gate and the production build; e2e plays the whole game headless; deploy waits for both.

Because a push to main is a release, the team rule is that npm run typecheck, npm test and npm run build all pass before you push. The release gate (tools/release-check.mjs) makes sure no placeholder tolerance used by the e2e runner leaks into src/.

package.json has devDependencies only (typescript, vite, vitest, playwright) and no dependencies at all. The shipped game is your code plus the browser. (The one exception is this documentation page, which loads a pinned Mermaid build from a CDN at runtime to draw its diagrams; the game never does.)

Why no UI framework? The game draws everything itself into one canvas, so a DOM framework has nothing to manage. What a framework would give you (components, state, lifecycle) is replaced by three small engine ideas you will meet in Architecture: the scene stack, the GameContext and the UiKit.

Advanced: what the constraints cost, and what they buy
  • Zero runtime dependencies means the input layer, the scene stack, the bitmap font, the menus, the audio synth and a PNG/zip toolchain for the Tile Lab are all in-house. The pay-off is that nothing upstream can change the game's behaviour, the bundle is small, and every system is readable in one sitting. Adding a runtime package is a project decision, not a local one.
  • A fixed 160×144 screen pushes constraints into content: dialogue must fit 18 columns × 2 lines, and src/world/validate.ts fails the test suite when a script line can't fit. Scaling is done in device pixels (see layout) so pixels stay square at fractional devicePixelRatios.
  • Strict TypeScript and shared id lists (src/contracts/ids.ts) turn typos in content into compile errors: a map that names an unknown MusicId or species doesn't build.
  • Python in the repo is pinned (tools/art/requirements.txt) because a Pillow or NumPy upgrade can change PNG bytes, and build_all.py --regen must leave git status clean.

Advanced: why the folders are cut this way

The project was built by several coding agents working in parallel, one per area (engine, battle, data and audio, world, art), each owning its directories (docs/ARCHITECTURE.md, "Ownership"). The cut follows those owners, which is why, for example, the options screen lives in src/screens/ while the text box lives in src/ui/. The rule "import other modules only through their entry points, and shared types only from src/contracts" is what let them work without stepping on each other. In practice there are deep imports (for example src/screens reads src/battle/logic/* directly); see module boundaries for the real graph and how to change it safely.

Quick start

From AGENTS.md:

npm ci
npm run dev                 # http://localhost:5173
npm run typecheck           # strict tsc
npm test                    # vitest, about 1670 tests: data, world validation, puzzles, balance, art bundles
npm run build               # typecheck + production bundle (relative base, for GitHub Pages)
npx playwright install chromium # first use: install the e2e browser
npm run e2e                 # headless full playthrough, 218 beats, speed 8, seed 1, daytime
npm run e2e -- --seed 42    # replay another RNG seed (unsigned 32-bit integer)
npm run art:index           # REQUIRED after adding, removing or renaming any file under public/art/

Useful first URLs on the dev server (all flags are listed in dev scenes and URL flags):

  • /: the real game, title screen first.
  • /?dev=ui: the UI showcase (font sheet, text box speeds, menus, name entry).
  • /?dev=battle: a hub of fixture battles. /?dev=audio: a jukebox.
  • /?dev=world&play=1&map=route_1: drop straight into a map.
  • /?dev=art: the Art Lab.
Before you finish any change, run npm run typecheck, npm test and npm run build. If you touched anything under public/art/, also run npm run art:index.

The pages, and how Vite builds them

Each page is a plain HTML file whose only script is a TypeScript entry module. Vite treats every listed HTML file as a separate input, bundles what each one imports, shares common chunks between them, and copies public/ into dist/ unchanged.

PageEntry moduleWhat it is
index.htmlsrc/main.tsThe game: one <canvas id="screen" width="160" height="144"> plus the bezel.
guide.htmlsrc/guide/main.tsThe strategy guide (walkthrough, Field Herbarium, moves, items, type chart), generated in the browser from DATA and WORLD.
tilelab.htmlsrc/tilelab/main.tsThe Tile Lab: every map drawn under the current tiles, tile and tileset swaps, art-pack export. Its "Walk around" button opens the game with ?tilelab=1.
devdocs.htmlsrc/devdocs/main.tsThis page: fragments in src/devdocs/sections/, loaded in file-name order by the page shell, with charts computed from the game's modules.

The four inputs in vite.config.ts:

export default defineConfig(({ command }) => ({
  base: command === "build" ? "./" : "/",
  plugins: [devdocsSource()],
  build: {
    rolldownOptions: {
      input: {
        main: fileURLToPath(new URL("./index.html", import.meta.url)),
        guide: fileURLToPath(new URL("./guide.html", import.meta.url)),
        tilelab: fileURLToPath(new URL("./tilelab.html", import.meta.url)),
        devdocs: fileURLToPath(new URL("./devdocs.html", import.meta.url)),
      },
    },
  },
}));

The one plugin, devdocsSource(), serves a virtual module (virtual:devdocs-source) with folder sizes, imports between src/ folders and test counts for this page's charts. Only devdocs.html imports it, so the game bundle never contains the source.

Advanced: relative base, runtime fetches and code splitting
  • Relative base. base: "./" for builds means every emitted URL is relative, so the same dist/ works at /verdant-reach/ on Pages or from any folder. Runtime art URLs are already relative (art/…), so only the HTML's root-absolute links need Vite's rewriting. Never hard-code a leading / in a runtime fetch.
  • Art is not bundled. The art registry fetches art/index.json, every bundle JSON, and PNGs on demand from the copied public/art/. That is what makes art swappable without a rebuild, and why npm run art:index must be re-run after file changes: an un-indexed file is invisible.
  • Lazy chunks. main.ts uses import.meta.glob("./*/dev.ts") and dynamic import()s (the title, new game, overworld, the Tile Lab hook, e2e), so these become separate chunks loaded only when used. The test hooks (the window.__vr handle, the dev driver, ?e2e, ?seed, ?speed) are on only in the dev server and the e2e build (--mode e2e, which the playthrough plays); the public production build ignores them and drops the playthrough chunk.

Advanced: vocabulary traps in the code
  • "growth" means evolution in screens and flows (screens/flows/growth, the growth jingle) but growthRate is an EXP curve. Name new things after the concept you mean.
  • Trigger names keep the old vigor spelling even though the in-game word is Vigour. Ids are stable once used in data and saves; don't "fix" them.
  • Ids are contracts. Adding a species, Mark, music track or SFX means adding it to the lists in src/contracts/ids.ts, which every module compiles against. Adding content under an existing id is not a contract change.
  • Player look. The player is a boy or a girl (state.playerLook, missing in old saves = boy). Always draw the player through playerArt(state), never the player/player_back keys directly, and keep dialogue about the player neutral.
