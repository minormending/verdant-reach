The world and the overworld

Verdant Reach splits the world in two. src/world/ is data: every map, script and trainer, written as plain TypeScript objects. src/overworld/ is the engine that reads that data and turns it into a walkable Game Boy screen. The two meet only through the shapes in src/contracts/world.ts.

This split is why a map can be added without touching engine code, and why the world can be checked by a test (the validator) without opening a browser. If you remember one thing from this section: maps describe, the overworld decides.

WORLD is the single exported object (WorldData) built in world/index.ts. It holds maps, scripts, trainers, quests, the SEED GLIDE landing list (glide) and newGame, the starting position and script (the Herbarium roof at night, script prologue). Scripts from every chapter file are merged by mergeScripts, which throws on a duplicate id, so two writers can never silently overwrite each other's scene.

Coordinates are tile coordinates: x is the column (character index), y the row, both from 0 at the top-left. A tile is 16x16 pixels and the screen shows 10x9 tiles.

Keep the column ruler comment (// 0123456789…) above the rows when you edit a map. Every coordinate in warps, npcs and triggers is counted against it, and an off-by-one is the most common map bug.

Conditions: Cond and when()

Many fields take a Cond: a list of { flag, is } pairs that must all hold. Flags are named booleans in state.flags, and a flag that was never set counts as false. Writing the list by hand is noisy, so build.ts has when():

export const when = (spec: Record<string, boolean>): Cond =>
  Object.entries(spec).map(([f, is]) => ({ flag: f, is }));

And the engine's check, in overworld/map.ts, is one line:

export function checkCond(cond: Cond | undefined, flags: Record<string, boolean>): boolean {
  if (!cond) return true;
  return cond.every((c) => (flags[c.flag] ?? false) === c.is);
}

There is no OR and no NOT beyond is: false. If you need "A or B", write two entries (two NPCs, two triggers) or branch inside a script.

Conditions appear on: visibleWhen (NPCs), when (triggers), and every *When list: legendWhen, encountersWhen and musicWhen. Those three lists all follow the rule first match wins, otherwise the plain field is used.

Real examples: the Sugarbush grove's tapped maples (X) become plain maples once grove_cleared is set (legendWhen); Bloom Lake swaps to a calm encounter table and drops its red-lake music once lake_calmed is set; the Palm House empties its grass (encounters: {}) during a Chapter 8 scene.

Advanced: how legendWhen is applied, and its limits

refreshLegend() runs every frame (in update and draw) and is cheap because it builds a signature string from the active entries, cleared field-move cells and filled pits, and returns early when it hasn't changed. The signature also tells TileLayer when to rebuild its cached ground canvas. Matching entries are merged with merged = { ...list[i].legend, ...merged }, so for any one character the earliest matching entry wins.

The validator forbids a legendWhen from introducing a field-move tile or a pit, and requires every overridden character to exist in the base legend and be used in tiles. That keeps per-cell progress flags (pruned_…, filled_…) independent of story flags.

Important: the main reachability pass in validateWorld builds its grid from the base legend only. A legendWhen that turns a walkable character solid (or the other way) is not proved safe by the generic soft-lock check. Puzzles that rely on it (the Sugarbush valves, the Bramblegate hedge gates) have their own tests in puzzles.test.ts. If you add a flag-driven wall, add a test like those.

Build helpers: LEGEND, OUTDOOR and pickups()

Every map shares one character legend, LEGEND, in build.ts. That is why a T is a tree and a , is tall grass on every map, which makes maps readable at a glance. A map can still extend or override it ({ ...OUTDOOR, T: "aspen_tree" } in the Elder Grove).

export const LEGEND: Record<string, TileKey> = {

  ",": "tall_grass",

  "v": "ledge_down",
  "T": "tree",
  "E": "mat_exit",

  "{": "ice",
  "<": "root_gap",
  ">": "root_bridge",
  "ø": "pit",
  "Ø": "filled_pit",

/** Outdoor maps: structure footprints sit on grass, so scenery with soft edges
 *  (the well, the windmill, landmark trees) shows lawn rather than road. */
export const OUTDOOR: Record<string, TileKey> = { ...LEGEND, "@": "grass" };

The @ character marks a structure footprint. The structure's image covers it, so the only question is what shows through transparent edges: path indoors (LEGEND), lawn outdoors (OUTDOOR).

pickups() builds item balls. An item_pickup NPC with no script gives the item named by its id, says "found", and hides for good behind the flag picked_<map>_<npcId>:

export function pickups(list: { item: ItemId; x: number; y: number; n?: number }[]): NpcDef[] {
  return list.map((p) => ({
    id: p.n && p.n > 1 ? `${p.item}_${p.n}` : p.item,
    sprite: "item_pickup", x: p.x, y: p.y, facing: "down", movement: "static",
  }));
}

Use n when one map has two of the same item (glass_pod and glass_pod_2): NPC ids must be unique per map, and the picked flag is keyed by id. The file also holds the script shorthands (say, flag, ifFlags, moveNpc…) covered in Scripts, and lockedDoor() for a door with no interior.

Advanced: legend characters and pickup ids
  • One character, one code point. The runtime splits rows with Array.from (code points) while the validator's width check uses row.length (UTF-16 units). They agree for every character in LEGEND, including ø and Ø; an emoji or other astral character would make them disagree, so don't use one.
  • Adding a character. Check it is free in LEGEND first: a clash silently changes every map that uses it. A tile used on one map only can go in that map's own legend instead.
  • Pickup ids. pickupItem() in build.ts mirrors the engine's rule (strip a leading item_ and a trailing _N), and the validator uses it to check every script-less pickup gives a real item. The engine's pickup() is more forgiving (it tries several candidates), but don't rely on that.
  • lockedDoor() ends with movePlayer("down"), which ignores collision; it assumes the tile below the door is free, which the door rules already require.

A tile key ("water", "ledge_down") names both a 16x16 image and a set of tile props in TILES (contracts/ids.ts): walk, water, slide, ledge, encounter, interact and fieldMove. Movement reads only these props, never the art.

Autotile masks

Autotiling picks an edge variant of a tile from its neighbours, so a pond gets a shoreline and a hedge joins into one run without anyone placing corner pieces by hand. Tiles are grouped in AUTOTILE (constants.ts): water, pond_lily, reeds and bridge are all in the "water" group, so water flows under bridges and into reed beds.

For each cell the engine sets one bit per neighbour that is in the same group: N=1, E=2, S=4, W=8. A neighbour off the map counts as the same, so water touching the map edge doesn't draw a fake shore.

flowchart TB
  N["N neighbour bit 1"]
  W["W neighbour bit 8"]
  C(("cell"))
  E["E neighbour bit 2"]
  S["S neighbour bit 4"]
  N --- C
  W --- C
  C --- E
  C --- S
export function autotileMask(m: MapRuntime, x: number, y: number): number {
  const group = autotileGroup(tileAt(m, x, y));
  if (!group) return -1;
  const same = (nx: number, ny: number) => !inBounds(m, nx, ny) || autotileGroup(tileAt(m, nx, ny)) === group;
  return (same(x, y - 1) ? MASK.N : 0)
    | (same(x + 1, y) ? MASK.E : 0)
    | (same(x, y + 1) ? MASK.S : 0)
    | (same(x - 1, y) ? MASK.W : 0);
}

14E S WShore along the north edge
11N E WShore along the south edge
6E STop-left corner of a pond

The image for mask m is ${key}@${m}.png. Art may supply any subset of the 16 masks, so the resolver in autotile.ts falls back step by step:

  A["autotiled tile, mask m"] --> V{"key@m.png exists?"}
  V -->|"yes"| VD["draw the edge variant"]
  V -->|"no"| ALT{"key~1..3.png exist?"}

  ALT -->|"yes"| H["pick one by position hash (base tile weighted double)"]

Advanced: variation, animation and caching
  • Edge variants beat ground variants. An alt (~1…~3) is only used when the cell would otherwise draw the plain base tile.
  • Stable randomness. pickAlt uses posHash(x, y), a 32-bit integer hash, never Math.random, so a field looks the same every visit and in the Tile Lab. It re-rolls once when it would repeat its west neighbour, which breaks up horizontal stripes.
  • Animation never pops. An animated tile (with __2.png) only uses an alt that has its own second frame.
  • Caching. TileCatalog memoises which alts exist per key. The ground is drawn into a cached layer that rebuilds only when the legend signature changes.
  • Groups can lie on purpose. vault_portal is in the "cliff" group so the portal reads as rock until the stair breaks it. stepping_stones join the water group so the river flows round them. When you add a tile, choose its group by what it should look joined to, not by what it is.

The overworld scene

The overworld is one big class, Overworld, created by createOverworldScene(ctx, opts) in overworld/index.ts. It is a scene on the engine's scene stack: it gets update() 60 times a second and draw(g) once per frame. Most of the pure rules live in small, unit-tested modules next to it (map.ts, raft.ts, ice.ts, uproot.ts, encounters.ts, roaming.ts, follower.ts); the class wires them together.

Two ideas explain most of the code:

  • busy and flow(). Anything that takes time (a text box, a battle, a script, a warp fade) runs inside flow(fn), which increments busy. While busy > 0 the player has no control and NPCs don't wander. When the last flow finishes, settle() tidies up: it clears a forgotten still, pans the camera back and fades in if a script left the screen black.
  • The grid is the truth. An actor's x, y jump to the destination tile the moment a step starts (Actor.begin); the smooth 16-pixel slide is only drawing. So collision, sight lines and triggers always reason about whole tiles.
flowchart TD
  U["update() each frame"] --> RL["refreshLegend"]
  RL --> TK["tick NPCs, follower, player"]
  TK --> AR{"player step just finished?"}
  AR -->|"yes"| OA["onArrive()"]
  AR -->|"no"| BZ
  OA --> BZ{"busy or dead?"}
  BZ -->|"yes"| STOP["return: a flow owns the screen"]
  BZ -->|"no"| SEED{"a seed ready to sprout?"}
  SEED -->|"yes"| SP["flow: sprout scene"]
  SEED -->|"no"| NPCS["updateNpcs()"]
  NPCS --> IN{"player standing still?"}
  IN -->|"yes"| HI["handleInput()"]
Advanced: invariants of the scene loop
  • Mutate state inside a flow. Long actions (talk, battle, warp) start with void this.flow(...) and return at once; the next frame sees busy > 0 and skips input. Starting async work outside flow() lets the player walk away mid-scene.
  • dead is set in exit() so a flow that resolves after the scene was replaced (the title, after endSlice) doesn't touch a scene that is gone.
  • Draw order is a Y-sort. Structures sort by the bottom of their footprint, characters by their feet, the follower just behind the player, so you walk behind roofs and in front of their bases. Tall grass is drawn again over the feet of anyone standing in it.
  • Cost per frame is small and linear: NPC lookups are Array.find over the map's NPCs, the ground is a cached canvas, and refreshLegend exits early when its signature is unchanged. Maps carry tens of NPCs, not thousands; if that ever changes, index NPCs by tile.
  • Missing map. Warping to an undefined map logs an error and stays on the current map (or falls back to the new-game map) instead of crashing.

Movement and collision

handleInput() reads the d-pad. A quick tap turns in place (5 frames of grace before walking); holding walks. A walk step takes 8 frames. Holding B runs, ramping 6, 5 then 4 frames per tile over the first steps. START opens the menu and A interacts with the tile in front.

Every attempted step goes through a pure function that answers "what happens if something at (x, y) moves one tile this way?" On land that is tryMove(); with the raft in the bag, tryRaftMove() wraps it.

export function tryMove(
  m: MapRuntime, x: number, y: number, dir: Dir,
  occupied: (x: number, y: number) => boolean = () => false,
): MoveResult {
  const { dx, dy } = DIRS[dir];
  const nx = x + dx;
  const ny = y + dy;
  if (!inBounds(m, nx, ny)) return { kind: "blocked", reason: "edge" };
  const props = tileProps(tileAt(m, nx, ny));
  if (props.ledge && !m.solid.has(key(nx, ny))) {
    if (dir !== props.ledge) return { kind: "blocked", reason: "ledge" };
    const lx = nx + dx;
    const ly = ny + dy;
    if (!isWalkable(m, lx, ly)) return { kind: "blocked", reason: "wall" };
    if (occupied(lx, ly)) return { kind: "blocked", reason: "occupied" };
    return { kind: "ledge", x: lx, y: ly };
  }
  if (!isWalkable(m, nx, ny)) return { kind: "blocked", reason: "wall" };
  if (occupied(nx, ny)) return { kind: "blocked", reason: "occupied" };
  return { kind: "walk", x: nx, y: ny };
}

isWalkable says yes for a structure's door, no for the rest of its footprint, and otherwise asks the tile's walk prop. A blocked move bumps (with a sound at most every 16 frames), unless the player is standing on a warp and pushing outward: that uses the warp. Exit mats only fire when you walk down, as in Crystal.

When a step finishes, onArrive() decides what the new tile does. The order matters, and it is the same every step:

Advanced: the tricky edges of RAFT, UPROOT, GLOW and GLIDE
  • Raft through warps. useWarp builds the destination map first and keeps rafting only if the arrival tile is water. Script warps and SEED GLIDE always land you on foot.
  • Ice never mounts a raft. Sliding into water is blocked; mounting is always an explicit A plus a yes.
  • Boulders are actors, pits are flags. Boulder positions live only in the current Actor list, which loadMap rebuilds from the MapDef. Leaving the room resets the puzzle. Filled pits live in flags and stay filled. Because of the reset, CONTINUE on a boulder map moves the player to the room's entrance (continue.ts) instead of behind a stone that has gone back to its start.
  • GLOW is drawing only at runtime. Nothing stops you walking in the dark; you just can't see. The validator is stricter on purpose: before the lantern is obtainable it treats dark tiles as solid, so every story path must be lamp-lit.
  • SEED GLIDE needs evidence of a visit. visitedGlideMaps() infers the furthest town from the position, heal point, marks, items and story flags, so old saves made before visited_* flags still get their towns. It is a monotone "furthest chapter reached" scan over a linear route; a future non-linear town would need a different rule.

NPCs, movement and trainer sight

An NpcDef is anything that stands on a tile and can be faced: people, animals, item balls, levers, boulders, berry bushes. The sprite and the id carry conventions the engine understands:

trainer instead of scriptThe engine runs intro, battle and the after line itself (and, for route trainers outdoors, offers a rematch).

Visibility is evaluated live, every frame, from visibleWhen. An invisible NPC is neither drawn nor solid. The script ops showNpc and hideNpc set a temporary override that lasts until the map is reloaded.

hideNpc is not saved. If a character should stay gone, set a flag and give the NPC a visibleWhen on it; use hideNpc only for the moment the scene ends. The PIP demo below does both.

Movement modes

  • static (the default): never moves on its own.
  • look_around: every 70 to 160 frames, faces a new random direction. A trainer re-checks its sight line each time it turns.
  • wander: every 50 to 180 frames, tries one step in a random direction, but never more than 2 tiles from its home tile, and never onto a warp or a trigger.

NPCs avoid the player, each other and the follower (occupiedForNpc). The player is only blocked by NPCs, never by the follower.

Trainer sight

An unbeaten trainer (no beat_<trainerId> flag) looks along its facing direction for up to sight tiles (default 4). Anything unwalkable or another NPC in between blocks the line.

export function inSight(
  m: MapRuntime, x: number, y: number, dir: Dir, range: number,
  target: { x: number; y: number }, blocked: (x: number, y: number) => boolean,
): number {
  const { dx, dy } = DIRS[dir];
  for (let i = 1; i <= range; i++) {
    const tx = x + dx * i;
    const ty = y + dy * i;
    if (tx === target.x && ty === target.y) return i;
    if (!isWalkable(m, tx, ty) || blocked(tx, ty)) return 0;
  }
  return 0;
}

Route rematches

Talking to a beaten trainer runs beatenTrainerTalk in rematchFlow.ts: the after line, then, if the trainer is eligible, a YES/NO question with the trainer's name as speaker. Sight never re-triggers a beaten trainer (checkTrainers skips every beat_<id>), so a rematch only ever starts from a talk.

await ctx.ui.say(tr.after);
if (!isRematchTrainer(ctx.world, trainerId)) return null;
if (!(await ctx.ui.yesNo(rematchPrompt(tr)))) return null;
const wins = ctx.state.trainerRematches?.[trainerId] ?? 0;
const result = await host.battle({
  kind: "trainer", trainer: trainerId, trainerDef: buildRematch(ctx.data, tr, wins), backdrop: host.backdrop?.(),
});
if (result === "won") ctx.state.trainerRematches = { ...ctx.state.trainerRematches, [trainerId]: wins + 1 };
else if (result === "lost") await host.whiteout();

Who is eligible is decided in one place, rematchTrainerIds in rematches.ts: an NPC with a trainer on a map with outdoor: true, whose trainer is not a rival (rival_*), not ROOTSTOCK (grunts and admins), has no mark and plain trainer music (no leaders, Council or Keeper), and is not battled by any script. Today that is the 43 route trainers on Routes 1 to 12; indoor trainers (Conservatory juniors, the Palm House) keep the after line only. The team, levels and growth are in the battle section.

A new route trainer becomes rematchable automatically. The test in rematches.test.ts lists every eligible id, so adding one means adding it to that list too, which makes the change deliberate.
Advanced: NPC invariants worth knowing
  • Scripted moves ignore collision. The moveNpc and movePlayer host methods step along the path without checking walls (a cutscene must never stall). Nothing validates those paths, so walk them in the game after you write them.
  • Trainers are checked after triggers. On a tile with a trigger, the trigger's script runs and the trainer check waits for the next step.
  • NPC ids are per map. Script ops refer to NPCs by id on the current map. The validator only checks that the id exists on some map, so a typo that matches another map's NPC passes; the engine then logs no npc "…".
  • Set dressing must not gate. Bushes, Nursery boarders and quest NPCs are checked by mustNotBlock: with all of them standing, every tile reachable without them must still be reachable.

The follower

The follower is the lead Quickened walking one tile behind you, drawn with its 16x16 party icon (follower.ts). It is the first healthy party member (a seed rolls along too), or the lead if all have wilted. It hides when the option is off or you are rafting.

  • It always heads for the tile the player just left.
  • A straight two-tile gap (you hopped a ledge) is crossed with a hop; any other gap (a warp, a scripted teleport) pops it in at the target.
  • After a map load it is tucked into your tile, hidden, and pops out on your first step, as in HeartGold.
  • It never blocks you or scripts. Face it and press A to hear how it is doing (followerLine, based on friendship, HP, status, time and whether its species likes the hour).
  • It performs field tools when it is out.
Advanced: follower edge cases
  • Queued steps catch up. If the player starts a new step before the follower finishes its last, the step is queued, then run faster (dur - age, at least 3 frames), so running never leaves it behind.
  • It occupies two tiles mid-step. occupies() is true for the tile it is leaving as well as the one it is entering. Wanderers and animals use this to step around it.
  • After the raft. On dismount it stays tucked until the player steps off a land tile, so it never appears to walk on water.
  • Seeds and wilted leads. A Nursery seed rolls along as the follower and talking to it gives a hint about the steps left. A wilted lead is still shown, one pixel lower, if no one is healthy.

Wild encounters

A step onto an encounter tile rolls once. The tile's props decide the encounter kind: grass (tall grass, snow), bog, or water (only while rafting). Ice never rolls. The table is encountersWhen's first match, else encounters.

export function rollEncounter(
  map: Pick<MapDef, "encounters" | "encountersWhen">, tile: TileKey, tod: TimeOfDay, rng: () => number,
  rafting = false,
  flags: Record<string, boolean> = {},
): { species: SpeciesId; level: number; kind: EncounterKind } | null {
  const kind = encounterKindFor(tile, rafting);
  if (!kind) return null;
  const match = map.encountersWhen?.find((entry) => checkCond(entry.when, flags));
  const table = (match ? match.encounters : map.encounters)?.[kind];
  if (!table || table.rate <= 0) return null;
  if (rng() * 100 >= table.rate) return null;
  const slot = pickWeighted(filterSlots(table.slots, tod), rng);
  if (!slot) return null;
  return { species: slot.species, level: rollLevel(slot, rng), kind };
}
  • Rate is a percentage per step. Most grass tables use 12; the range in the game is 10 to 20.
  • Slots are weighted, not percentages: on Route 1 by day the weights are 35+25+25+15+8 = 108, so a dandelion is 35/108, about 32%. Weights are relative, so adding a slot quietly lowers every other chance.
  • Time: a slot's time is "any" (default), "day" (morning and day) or "night". Time comes from mapTime(): the map's forced time, else the real clock (morning 4–10, day 10–18, night 18–4).
  • Level is uniform between minLevel and maxLevel inclusive.

Advanced: encounter invariants the validator enforces
  • Every table (base and conditional) must have at least one slot active by day and one by night, so time of day can never empty a patch of grass.
  • Any map with tall grass or snow must have a grass table; any map with bog must have a bog table.
  • minLevel may not exceed maxLevel, and every species must exist in SPECIES_IDS.
  • Weights of 0 are filtered out, which is a handy way to switch a slot off in an encountersWhen copy.
  • Balance across the story is covered by balance.test.ts; keep it green when you raise or lower a route's levels.

Roaming Wanderers and BURR's hitchhike

After the game is cleared, three legendary Wanderers are let loose (flags game_cleared and wanderers_free). The rules are pure functions in roaming.ts; randomness and the calendar date are passed in, which makes them easy to test.

BURR (a burdock bur, which really does travel by sticking to passers-by) works differently. On each entry to an outdoor route_N map, while BURR is free, the game rolls 1 in 8. If it wins, BURR is placed on the first safe tile straight behind the player. On arrival that tile is usually the exit warp, so the win is kept as pending and BURR catches up after 3 steps.

A tile is "safe" (burrTileSafe) if it is walkable, isn't a warp, and has at least one exit that isn't a warp, so BURR can never stand where it would block a door or a dead-end mat.

Advanced: immutability, saves and RNG draws
  • The roaming functions return new state objects ({ ...state, roamers: { ...state.roamers } }); the overworld merges them back with Object.assign(ctx.state, …). Keep that style, since the tests compare before and after.
  • burrRoll only draws from the RNG when BURR is free on an eligible map, so seeded e2e runs before the post-game see the same random stream as before BURR existed.
  • The wanderer's max HP uses fixed trainer DVs, so only current HP and status need saving.
  • burrHitch is kept through SAVE and CONTINUE, then cleared on the next map entry. A hitch on a map that is no longer valid (not a route, not safe, occupied) is dropped at load.
  • A "day" is the local date string YYYY-MM-DD; a clock set backwards cannot revive a wilted Wanderer (wilted >= day is skipped).

Healing, whiteout and onEnter

The heal script op heals the party and, if the current map has a healPoint, records it as state.heal. When you lose a battle you can't lose (canLose unset), whiteout() runs:

  1. Remember the losing map's onWhiteout.
  2. Fade to black, drop half your money, heal the party.
  3. Load state.heal, facing up, and fade in.
  4. Run the losing map's onWhiteout script. The Council seats use this to reset a failed run.

onEnter runs after the fade-in on every arrival: warps, script warps (after the script fades back in), SEED GLIDE and CONTINUE. Write onEnter scripts to be safe to run many times, usually by wrapping the scene in an ifFlags({ seen: false }, …) and setting seen inside.

Advanced: whiteout ordering and the built-in script
  • onWhiteout is read before loadMap swaps to the healing map; otherwise the healing map's own script would run.
  • "whiteout" is a reserved script id: call with it (or runScript("whiteout")) runs the recovery and throws ScriptAbort, so nothing after it runs. The validator accepts it although no such script exists in WORLD.scripts.
  • The heal point only changes through the heal op on a map with a healPoint. A new game starts with the player's home as its heal point, so a whiteout in the prologue goes home ("…and scurried back home!").
  • The Council uses onWhiteout to reset its run flags, including the engine's beat_<trainer> flags for the seats, so a lost run can't skip a seat next time (COUNCIL_RUN_FLAGS in ch11.ts).

The world validator

validate.ts is the reason the game can promise "no soft-locks". validateWorld(WORLD) returns a list of problems; world.test.ts expects it to be empty. It runs on the whole world in about a second, as part of npm test, so a bad warp fails CI before anyone plays it.

It reuses the engine's own rules (slidePathFrom for ice, reachableBoulderTiles for UPROOT, glowField for darkness) rather than re-implementing them, so the proof and the game can't drift apart.

How it proves it

Each map becomes a Grid: a walkability function built from the base legend and structure footprints, optionally with brambles cut, gaps bridged or water rideable. flood() is a breadth-first search over it that honours one-way ledges and ice slides. For soft-locks, canReach() runs the flood backwards from the warps, so one pass answers "can every tile still get out?" instead of one flood per tile.

// soft-lock: from every reachable tile some warp must still be reachable,
// both before the PRUNING SHEARS (brambles solid) and after (brambles cut).
if (map.warps.length) {
  for (const [gg, from, when] of [[g, flood(g, starts), "before PRUNE"], [gp, reach, "with PRUNE"]] as const) {
    // …
    const canExit = canReach(exits, map.warps);
    for (const k of from) {
      if (!canExit.has(k)) {
        errs.push(`${where} soft-lock ${when}: no exit from ${k}`);
        break;
      }
    }
  }
} else errs.push(`${where} has no warps`);

Progression is the clever part. progress() explores the whole world like a very patient player: start at newGame, flood the map, run every reachable NPC, trigger and onEnter script statically (collecting the flags they set, the items they give and the warps they make), follow warps to new maps, and repeat until nothing new turns up. That is a least fixed point.

To check a gate, the explorer runs a second time with that gate's item withheld and compares what each map can reach "before" with what it can reach "after". Content that only the gate opens, but which the story needs before the gate's item can be had, is an error, reported with the map and coordinate.

Advanced: what the validator does not prove, and performance
  • Static, optimistic scripts. The explorer takes every branch of every if, choice and battle as possible. It proves a path exists, not that a particular sequence of flags is consistent. Order-of-scenes bugs are what the 218-beat e2e playthrough is for.
  • Scripted movement. movePlayer, moveNpc and camera paths are not checked against walls.
  • legendWhen walls. Ordinary reachability uses the base legend; flag-driven walls need their own puzzle test.
  • Trainer lines are only checked for over-long words, not the 3-page limit that say gets.
  • Caching. Grids and floods are cached by a per-map signature of the gates that actually affect that map, so unlocking the raft doesn't re-flood a desert. Boulder rooms use a BFS over layouts that stops as soon as every potentially reachable tile has been seen; keep boulder puzzles small (a handful of stones), as the state space grows quickly.
  • Extending. A new tool is one more ProgressGate entry (affects, terrain, optional reach) and a checkProgressWithout… wrapper with a test. Reuse the runtime's pure movement function in terrain/reach rather than writing a second copy.

Adding a map, step by step

  1. Add the id to MAP_IDS in contracts/ids.ts (the validator loops over this list, so a map that isn't listed isn't checked).
  2. Create src/world/maps/<id>.ts exporting a MapDef. Copy a similar map; keep the column ruler.
  3. Register it in maps in world/index.ts, and put its scripts in the chapter's script file.
  4. Add warps both ways. A door's interior exit must land on the tile below the door.
  5. Run npx vitest run src/world. Read every error: each names the map, the coordinate and the rule.
  6. Walk it: npm run dev, then /?dev=world for the overview, and look at it in the Tile Lab.
