CI and deploy

CI (continuous integration) is a machine that runs the checks on every change so nobody has to remember to. CD (continuous deployment) is the step after: if the checks pass, publish. Verdant Reach has one workflow, .github/workflows/pages.yml, that does both. Every push to main is tested, played through headless and, only if everything passes, deployed to https://minormending.github.io/verdant-reach/.

The workflow runs only on pushes to main and on a manual run (workflow_dispatch). There is no pull-request or feature-branch trigger. Your branch is checked by you, locally, before you merge; CI is the final gate, not a safety net for untested branches.

A job is a group of steps that runs on its own fresh virtual machine (ubuntu-latest). Steps inside a job run in order and stop at the first failure. Jobs run in parallel unless one needs another. Here build and e2e start together, and deploy waits for both.

  contents: read
  pages: write

# One run at a time: a newer push cancels any queued or running one
# (cancel-in-progress), so only the newest commit deploys.
concurrency:
  group: pages
  cancel-in-progress: true
# …
  deploy:
    needs: [build, e2e]
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5

The permissions are the minimum Pages needs: read the code, write Pages, and an OIDC token (id-token: write) that proves to Pages the artifact came from this workflow.

Advanced: concurrency and timeouts

concurrency: { group: pages, cancel-in-progress: true } means at most one run of this workflow is active, and a newer push cancels the current one whether it is queued or already running, including a playthrough 40 minutes in. Two pushes ten minutes apart therefore deploy only the second; the first shows as cancelled, not failed. That is what you want for a deploy, but it means a run that never finished proves nothing about its commit.

sequenceDiagram
  participant A as push A
  participant GH as Actions, group pages
  participant B as push B
  A->>GH: run A starts build and e2e
  B->>GH: run B queued
  GH-->>A: run A cancelled
  GH->>GH: run B runs build and e2e
  GH->>GH: run B deploys

There are two timeouts on the playthrough. The runner's own limit is max(75, 360 / speed) minutes, so 75 at the default speed 8; the job's limit is 90. The runner times out first, which matters: it still writes the report and the if: always() upload keeps it. If the job limit fired first, GitHub would kill the process and the report would be lost. Keep the job limit above the runner's.

Each job runs npm ci on a clean machine with the package-lock.json versions, Node 22 and Linux. A test that passes on your Mac but depends on a newer Node, the local time zone or a file you forgot to commit fails here.

GitHub Pages deploy

GitHub Pages serves static files. The game is static files: npm run build writes dist/ with index.html, every other page listed in build.rolldownOptions.input in vite.config.ts (the guide and the Tile Lab), the bundled JavaScript and everything from public/, art included. The build uses a relative base (./), so the site works under the /verdant-reach/ sub-path without any configuration.

sequenceDiagram
  participant Dev as developer
  participant Git as GitHub main
  participant B as build job
  participant E as e2e job
  participant D as deploy job
  participant P as Pages site
  Dev->>Git: git push origin main
  Git->>B: start
  Git->>E: start
  B->>B: test, release-check, build
  B->>Git: upload-pages-artifact dist
  E->>E: vite build --mode e2e, then the 218-beat playthrough
  B-->>D: success
  E-->>D: success
  D->>P: deploy-pages publishes the artifact
  P-->>Dev: live at minormending.github.io/verdant-reach

Test-only code never reaches the site. The playthrough, the dev driver and the ?seed, ?speed and ?e2e parameters are on only when import.meta.env.DEV or import.meta.env.MODE === "e2e" (testHooks.ts). Vite replaces both at build time, so in the Pages build (mode production) the parameters are ignored and the playthrough chunk is not emitted at all. The ?dev= scenes are different: they are loaded on demand in every build (the Art Lab works on the live site).

Advanced: what is actually deployed, and rolling back

The deploy job does not build anything. It publishes the artifact the build job uploaded, so the site is exactly the dist/ that passed typecheck, tests and release-check in that run, and the playthrough ran against the same commit in parallel. The e2e job plays a production build of that commit: vite build --mode e2e runs the same bundling, chunk splitting, minification and relative base as dist/, served by vite preview, so production-only bugs fail the playthrough. It is not byte-for-byte the deployed artifact: the mode differs, which switches on the test hooks (and only them). Open the live site after a release that touches those hooks.

To roll back, push a revert commit to main. It goes through the same gate, which is slower than clicking a button but means a rollback can never ship something untested.

What blocks a deploy

Because deploy needs both jobs, any red step anywhere stops the site from changing. The live site keeps serving the last good build.

Reading a failed run

Start from the red step, not from the top of the log. The runner prints one line per beat (OK or FAIL, the time in seconds, the name, a note), one ISSUE kind time @map@x,y: message line per issue, and a final count. With the GitHub CLI:

gh run list --workflow pages.yml --limit 5      # find the run
gh run view <run-id> --log-failed               # only the failed steps' logs
gh run download <run-id> --name e2e-report      # last-report.json

# Which beats failed, and what went wrong?
jq '.beats[] | select(.ok | not) | {name, note, map, pos}' last-report.json
jq '.issues' last-report.json
jq '.runner' last-report.json                   # speed, seed, elapsed, runner issues
jq '.texts[-20:]' last-report.json              # the last 20 lines of dialogue

Each beat in the report carries a screenshot (shot, a PNG data URL). Paste the one from the failed beat into a browser's address bar to see exactly what the screen showed.
Advanced: reproducing a CI failure

The report's runner.seed and runner.speed are the whole input. npm run e2e -- --seed <seed> --speed <speed> replays the same battles. If it passes locally and fails in CI, compare runner.elapsedSeconds and the frame stats: a much slower CI run points at timing, not logic. If it fails locally right after a jingle and passes in CI, see the stalled audio clock under the playthrough.

A manual re-run from the Actions page (or a workflow_dispatch) rebuilds and redeploys the same commit; it does not need a new push. Use it for a timing flake, never to "try again" on a deterministic failure.

Branches and the release rule

main is the release branch: whatever is on it goes live as soon as the pipeline passes. Everything else happens on feature branches named after the work:

The usual shape, simplified: a chapter branch carries placeholders while the work is in progress, art passes branch from it and merge back, and the chapter reaches main only once its writing pass has removed every placeholder.

The rule: main must pass npm run release-check. Placeholders (stand-in dialogue, placeholder art) are fine on a feature branch, where the playthrough runs with --allow-placeholders, and must all be gone before the merge. In practice, before merging to main:

  1. npm run typecheck, npm test and npm run build pass.
  2. npm run release-check prints release-check: OK.
  3. npm run e2e passes without --allow-placeholders if gameplay changed.
  4. If art changed: build_all.py --regen leaves git status clean.
  5. The README's scope and features, and AGENTS.md where commands or counts changed, are updated in the same merge.

Commit style

Commits are small and logical: one idea each, so a reviewer (or git bisect) can understand and revert them one at a time. The summary line is imperative, like a command ("Ask … at NEW GAME", not "Asked" or "Asking"), and the body explains why, plus anything a reviewer could not guess from the diff. A real example:

Check the BOY choice in the e2e new game (217 beats)

The playthrough now passes the boy/girl question by taking the cursor's
default, BOY, so the rest of the run and its baselines are unchanged. A
new beat confirms the question was asked, the look and default name were
set (SORREL), and the overworld player walks with the boy's sheet. The
GIRL path is covered by unit tests. The beat count moves to 217 in the
runner, its tests, the workflow, AGENTS.md and the README.
  • Work done by a delegated agent is prefixed delegate(codex): … and names the plan section it implements.
  • Commits written with an AI assistant end with a Co-Authored-By: trailer.
  • Push to main only when typecheck, tests and the build pass: a push deploys the site.
Advanced: why the gate is on main, not on branches

The playthrough is too slow to run on every branch push, and feature branches are allowed to be unfinished (that is what --allow-placeholders is for). Putting the full gate on main only keeps CI cheap and the rule simple: what is on main is finished, tested and live. The cost is that a broken branch is found late, which is why the merge checklist above is run locally first.

If main ever goes red, the site stays on the last good build, so nothing is lost for players; but every later push is blocked until it is green again. Fix forward with a small commit rather than force-pushing: rewriting main's history breaks every branch cut from it.
