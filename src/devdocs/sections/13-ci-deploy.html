CI and deploy

CI (continuous integration) is a machine that runs the checks on every change so nobody has to remember to. CD (continuous deployment) is the step after: if the checks pass, publish. Verdant Reach has two workflows. .github/workflows/pages.yml does both CI and CD: every push to main is unit-tested, built, smoke-tested in a headless browser and, only if everything passes, deployed to https://minormending.github.io/verdant-reach/. .github/workflows/playthrough.yml plays the whole game every night and never deploys.

The deploy workflow runs only on pushes to main and on a manual run (workflow_dispatch); the playthrough runs on a schedule and on a manual run. There is no pull-request or feature-branch trigger. Your branch is checked by you, locally, before you merge; CI is the final gate, not a safety net for untested branches.

A job is a group of steps that runs on its own fresh virtual machine (ubuntu-latest). Steps inside a job run in order and stop at the first failure. Jobs run in parallel unless one needs another. Here changes and build start together; smoke starts once changes has decided (in seconds), so it too runs alongside build; deploy waits for all three.

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

# One run at a time: a newer push cancels any queued or running one
# (cancel-in-progress), so only the newest commit deploys.
concurrency:
  group: pages
  cancel-in-progress: true
# …
  smoke:
    needs: changes
    if: needs.changes.outputs.smoke == 'true'
    runs-on: ubuntu-latest
    timeout-minutes: 30
# …
  deploy:
    needs: [changes, build, smoke]
    if: >-
      ${{ !cancelled()
      && needs.changes.result == 'success'
      && needs.build.result == 'success'
      && (needs.smoke.result == 'success'
      || (needs.smoke.result == 'skipped' && needs.changes.outputs.smoke == 'false')) }}
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5

The permissions are the minimum Pages needs: read the code, write Pages, and an OIDC token (id-token: write) that proves to Pages the artifact came from this workflow. The changes job sets its own, contents: read and actions: read, to look up this workflow's past runs.

The fast lane

Some files can't change how the game plays: the docs, the guidebook, the developer docs, the Tile Lab, the Trainer Editor and the art review sheets. A push that changes only those takes the fast lane: the smoke job is skipped and the site deploys as soon as build (unit tests, release-check and the bundle) passes. The changes job compares the push's previous tip, github.event.before, with github.sha and matches every changed path against this list:

PathWhat it is
docs/**, any *.mdDocs, the README, AGENTS.md, the docs contract
src/guide/**, guide.htmlThe guidebook
src/devdocs/**, devdocs.htmlThese developer docs
src/tilelab/**, tilelab.htmlThe Tile Lab
src/trainereditor/**, trainereditor.htmlThe Trainer Editor
tools/art/review/**Art review sheets

Why these are safe: the game never imports the guidebook or the developer docs, and it loads the Tile Lab and Trainer Editor hooks (src/tilelab/hook.ts, src/trainereditor/hook.ts) only behind ?tilelab and ?trainerlab, the opt-in "walk around" and "play with these trainers" links (src/main.ts). The build job still runs every unit test, including these pages' own, and the bundle. Keep it that way: game code that a tool page needs belongs in the game's folders, never the other way round.

Advanced: before, skipped needs and the deploy condition

github.event.before is the branch's tip before the push. On the very first push of a branch it is forty zeros, and on a manual run there is no push event at all, so both run the smoke test. After a force-push, before may not be an ancestor of the new tip (and the event's forced is true), so that runs it too. A push of several commits is diffed as a whole, before to sha, so one game change among them sends the whole push through the smoke test. The diff uses --no-renames, so a moved file counts at both its old and new path.

A base that never passed. Diffing against before alone would leak: push A changes the game, push B (docs only) arrives and cancels A's run, and B's fast lane would deploy A's game change untested. So the job also asks the API whether a run of this workflow for before succeeded (gh api …/workflows/pages.yml/runs?head_sha=…&status=success); if it failed, was cancelled or can't be checked, the smoke test runs. By induction every deployed commit is then either smoke-tested or differs from a deployed one only in the list above. An empty diff (an empty commit pushed to retry) also runs it.

Skipped needs. A job whose needs include a skipped or failed job is itself skipped unless its if: uses a status function. That is why deploy starts with !cancelled() (not always(), which would still deploy a run cancelled by a newer push) and then states the rule itself: build succeeded, and smoke succeeded or was skipped. A skipped smoke counts only when changes succeeded and said smoke=false: if changes fails, smoke is skipped too, and that must never deploy. That is the only reason deploy needs changes. smoke's own if: has no status function, so it gets the implicit success() and runs only when changes succeeded and chose it.

Advanced: concurrency and timeouts

concurrency: { group: pages, cancel-in-progress: true } means at most one run of this workflow is active, and a newer push cancels the current one whether it is queued or already running, including a smoke test halfway through. Two pushes a minute apart therefore deploy only the second; the first shows as cancelled, not failed. That is what you want for a deploy, but it means a run that never finished proves nothing about its commit.

sequenceDiagram
  participant A as push A
  participant GH as Actions, group pages
  participant B as push B
  A->>GH: run A starts build and smoke
  B->>GH: run B queued
  GH-->>A: run A cancelled
  GH->>GH: run B runs build and smoke
  GH->>GH: run B deploys

There are two timeouts on each browser test. The smoke test's runner limit is 20 minutes and its job's is 30; the full playthrough's runner limit is max(75, 360 / speed) minutes, so 75 at the default speed 8, and its job's is 90. The runner times out first, which matters: it still writes the report and the if: always() upload keeps it. If the job limit fired first, GitHub would kill the process and the report would be lost. Keep each job limit above its runner's.

Each job runs npm ci on a clean machine with the package-lock.json versions, Node 22 and Linux. A test that passes on your Mac but depends on a newer Node, the local time zone or a file you forgot to commit fails here.

GitHub Pages deploy

GitHub Pages serves static files. The game is static files: npm run build writes dist/ with index.html, every other page listed in build.rolldownOptions.input in vite.config.ts (the guide and the Tile Lab), the bundled JavaScript and everything from public/, art included. The build uses a relative base (./), so the site works under the /verdant-reach/ sub-path without any configuration.

sequenceDiagram
  participant Dev as developer

  B->>Git: upload-pages-artifact dist
  E->>E: vite build --mode e2e, then the 26-beat smoke test
  B-->>D: success
  E-->>D: success
  D->>P: deploy-pages publishes the artifact
  P-->>Dev: live at minormending.github.io/verdant-reach

Test-only code never reaches the site. The playthrough, the smoke suite, the dev driver and the ?seed, ?speed and ?e2e parameters are on only when import.meta.env.DEV or import.meta.env.MODE === "e2e" (testHooks.ts). Vite replaces both at build time, so in the Pages build (mode production) the parameters are ignored and the playthrough and smoke chunks are not emitted at all. The ?dev= scenes are different: they are loaded on demand in every build (the Art Lab works on the live site).

Advanced: what is actually deployed, and rolling back

The deploy job does not build anything. It publishes the artifact the build job uploaded, so the site is exactly the dist/ that passed typecheck, tests and release-check in that run, and the smoke test ran against the same commit in parallel (or the fast lane showed the commit differs from a deployed one only in docs and tool pages). The smoke job plays a production build of that commit: vite build --mode e2e runs the same bundling, chunk splitting, minification and relative base as dist/, served by vite preview, so production-only bugs fail the smoke test. It is not byte-for-byte the deployed artifact: the mode differs, which switches on the test hooks (and only them). Open the live site after a release that touches those hooks.

To roll back, push a revert commit to main. It goes through the same gate, which is slower than clicking a button but means a rollback can never ship something untested.

What blocks a deploy

Because deploy needs every job, any red step anywhere stops the site from changing. The live site keeps serving the last good build. The nightly playthrough never blocks a deploy; a red night is a bug to fix on main (see below).

The nightly playthrough

playthrough.yml runs npm run e2e, the full 218-beat playthrough of the production build, every night at 07:23 UTC (cron: "23 7 * * *": late night in the Americas, and off the top of the hour, when GitHub's scheduler is busiest), and whenever someone presses Run workflow on its Actions page. It keeps e2e/last-report.json as the e2e-report artifact and never deploys. Its concurrency group, playthrough, is its own, so it never cancels or waits on a deploy; with cancel-in-progress: false a manual run queues behind a running one instead of cancelling it most of the way through.

Before a risky release (a chapter, a map rework, battle or save changes), run the full playthrough yourself: npm run e2e locally, or the Playthrough workflow on main right after the merge. The smoke test covers the first hour of the game and the shared systems; only the full run reaches the late chapters and the post-game.
Advanced: what the nightly run catches, and what it doesn't

The nightly run plays whatever main is at that moment, so a red night means some commit since the last green night broke a late beat that the smoke test doesn't reach. The site is already live by then: fix forward with a small commit, the same as any other bug on main. gh run list --workflow playthrough.yml shows which night first went red, which narrows the commits to bisect.

GitHub runs scheduled workflows only from the default branch, and turns them off in a public repository after 60 days without activity; a push re-enables them.

Reading a failed run

Start from the red step, not from the top of the log. The runner prints one line per beat (OK or FAIL, the time in seconds, the name, a note), one ISSUE kind time @map@x,y: message line per issue, and a final count. With the GitHub CLI:

gh run list --workflow pages.yml --limit 5      # find the run
gh run view <run-id> --log-failed               # only the failed steps' logs
gh run download <run-id> --name smoke-report    # last-smoke-report.json (a deploy run)
gh run list --workflow playthrough.yml --limit 5
gh run download <run-id> --name e2e-report      # last-report.json (a nightly run)

# Which beats failed, and what went wrong?
jq '.beats[] | select(.ok | not) | {phase, name, note, map, pos}' last-report.json   # phase: smoke only
jq '.issues' last-report.json
jq '.runner' last-report.json                   # speed, seed, elapsed, runner issues
jq '.texts[-20:]' last-report.json              # the last 20 lines of dialogue

Each beat in the report carries a screenshot (shot, a PNG data URL). Paste the one from the failed beat into a browser's address bar to see exactly what the screen showed.
Advanced: reproducing a CI failure

The report's runner.seed and runner.speed are the whole input. npm run e2e -- --seed <seed> --speed <speed> replays the same battles (npm run e2e:smoke for a smoke failure: the same seed and speed). If it passes locally and fails in CI, compare runner.elapsedSeconds and the frame stats: a much slower CI run points at timing, not logic. If it fails locally right after a jingle and passes in CI, see the stalled audio clock under the playthrough.

A manual re-run from the Actions page (or a workflow_dispatch) rebuilds and redeploys the same commit, always with the smoke test; it does not need a new push. Use it for a timing flake, never to "try again" on a deterministic failure.

main is the release branch: whatever is on it goes live as soon as the pipeline passes. Everything else happens on feature branches named after the work:

The usual shape, simplified: a chapter branch carries placeholders while the work is in progress, art passes branch from it and merge back, and the chapter reaches main only once its writing pass has removed every placeholder.

The rule: main must pass npm run release-check. Placeholders (stand-in dialogue, placeholder art) are fine on a feature branch, where the playthrough runs with --allow-placeholders, and must all be gone before the merge. In practice, before merging to main:

  1. npm run typecheck, npm test and npm run build pass.
  2. npm run release-check prints release-check: OK.
  3. npm run e2e:smoke passes if gameplay changed, and npm run e2e passes without --allow-placeholders before a risky release (story, maps, battles, saving), or run the Playthrough workflow by hand.
  4. If art changed: build_all.py --regen leaves git status clean.
  5. The README's scope and features, and AGENTS.md where commands or counts changed, are updated in the same merge.

Commit style

Commits are small and logical: one idea each, so a reviewer (or git bisect) can understand and revert them one at a time. The summary line is imperative, like a command ("Ask … at NEW GAME", not "Asked" or "Asking"), and the body explains why, plus anything a reviewer could not guess from the diff. A real example:

Check the BOY choice in the e2e new game (217 beats)

The playthrough now passes the boy/girl question by taking the cursor's
default, BOY, so the rest of the run and its baselines are unchanged. A
new beat confirms the question was asked, the look and default name were
set (SORREL), and the overworld player walks with the boy's sheet. The
GIRL path is covered by unit tests. The beat count moves to 217 in the
runner, its tests, the workflow, AGENTS.md and the README.
  • Work done by a delegated agent is prefixed delegate(codex): … and names the plan section it implements.
  • Commits written with an AI assistant end with a Co-Authored-By: trailer.
  • Push to main only when typecheck, tests and the build pass: a push deploys the site.
Advanced: why the gate is on main, not on branches

The browser tests are too slow to run on every branch push, and feature branches are allowed to be unfinished (that is what --allow-placeholders is for). Putting the full gate on main only keeps CI cheap and the rule simple: what is on main is finished, tested and live. The cost is that a broken branch is found late, which is why the merge checklist above is run locally first.

If main ever goes red, the site stays on the last good build, so nothing is lost for players; but every later push is blocked until it is green again. Fix forward with a small commit rather than force-pushing: rewriting main's history breaks every branch cut from it.
