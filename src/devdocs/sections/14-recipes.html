Recipes

These are the common changes, written as checklists. Each one names the exact files to touch and the tests that will catch a mistake, so you can work in small steps and let the tests tell you what you missed. Two habits make all of them easier:

  • Start from the id. Most content begins with an id in src/contracts/ids.ts (SPECIES_IDS, MAP_IDS, TILES…). Those lists are contracts: types every module shares. Once the id exists, TypeScript and the tests point at every place that still needs it.
  • Copy a neighbour. Find the most similar existing species, map or trainer and copy its shape. Then run npm test early and often.
flowchart LR
  IDS["contracts: ids.ts, world.ts, runtime.ts"] --> DATA["src/data JSON"]
  IDS --> WORLD["src/world maps, scripts, trainers"]
  IDS --> ART["public/art bundles"]
  IDS --> ENGINE["src/overworld, src/battle, src/save"]
  DATA --> TESTS["npm test"]
  WORLD --> TESTS
  ART --> TESTS
  ENGINE --> TESTS
  TESTS --> E2E["npm run e2e when story or flow changed"]
src/contracts/ is owned by the coordinator and changed deliberately. Adding an id to a list is routine; changing a shape (a new field on MapDef, a new ScriptCmd op) is a contract change, so keep it minimal and say why in the commit.

Add a species

A species is one stage of a plant line (oak acorn, oak sapling, great oak). Its gameplay data and its art live apart: data in JSON under src/data/species/, art in a bundle under public/art/species/<id>/. Swapping art never changes gameplay, and editing data never changes art.

flowchart TB
  A["1. id in SPECIES_IDS"] --> B["2. data and Herbarium page in src/data/species/line.json"]
  B --> C["3. encounters in src/world/maps"]
  C --> D["4. art: tools/art/crystal/line.py, build.py line --sheet"]
  D --> E["5. npm run art:index"]
  E --> F["6. npm test"]
  F --> G["7. check in game with ?dev=world and play=1"]
  1. Id. Add it to SPECIES_IDS in ids.ts, next to its line.
  2. Data. Add an entry to the line's file in src/data/species/ (a new line gets a new file with its pollination groups). Stages go in order. The format is in docs/DATA.md. The herbarium page must hold one true, checkable fact about the real plant, stated in fact and cited in source.
  3. Encounters. Put it in a map's encounters table (grass, bog or water), with day and night coverage, or give it through a script (giveSpecies, wildBattle, trade).
  4. Art. Draw it in a tools/art/crystal/<line>.py module (copy a similar line), then run .venv/bin/python tools/art/crystal/build.py <line> --sheet. The rule checker must report 0 errors (four-colour palette, white share, no faces, an intro animation). Add its sport (shiny) in docs/SPORTS.md.
  5. Index. npm run art:index after adding files under public/art/.
  6. Check. npm test, then /?dev=world&play=1&map=route_1&species=<id>&level=40 to see its battle intro.

Advanced: changing an existing species

A Quickened's stats are stored in the save and recomputed from its species only on level-up, growth and in the Nursery, so a base-stat change reaches plants in players' existing saves at their next level-up or growth, not on load (stored stats). Ids are forever: renaming one breaks saves (party, box, Herbarium) and art folders. Add a new id instead. The learnset order matters for the starting moves (all level-1 entries) and for trainers without explicit moves, whose moves come from the learnset at their level, so a learnset edit can move a balance band.

Add a map and connect it with warps

A map is a grid of characters plus a legend that turns each character into a tile. A warp is a cell that moves the player to a cell on another map. Doors and exits come in pairs, and the validator checks both halves.

  1. Id. Add it to MAP_IDS in ids.ts.
  2. File. Create src/world/maps/<id>.ts exporting a MapDef. Use the shared LEGEND (indoors) or OUTDOOR from build.ts.
  3. Register. Import it in src/world/index.ts and add it to the maps record (TypeScript insists, because the record is Record<MapId, MapDef>). If the file exports scripts, add them to mapScripts.
  4. Warps both ways. A door warp on the outside map, and an exit on the inside map that lands on the tile below the door.
  5. Check. npm test, then /?dev=world&map=<id>, which lists validator problems and tints unreachable tiles red.

Advanced: maps already frozen by digests

Maps from Chapters 6 to 11 and the post-game are pinned by environment digest tests. Adding a warp to one of them changes its digest. That is an intended gameplay change, so re-pin the digest with a comment saying which warp you added and why. Keep the existing property order in edited objects. Add an NPC with a script and a flag

An NPC is anything on a map that can be talked to: people, signs-with-faces, levers, item balls. Its script is a list of ScriptCmd operations run when the player presses A facing it. A flag is a named boolean in the save (state.flags), snake_case, false until set; flags are how the story remembers.

  1. Place the NPC in the map's npcs: a unique id on that map, a sprite from CHARACTERS, a walkable cell, and a script id. Use visibleWhen to show it only in some story states.
  2. Write the script in the chapter's script file (src/world/scripts/chN.ts) with the helpers from build.ts: say, flag, ifFlags, moveNpc…
  3. Fit the text box: 18 columns by 2 lines, at most 3 pages per say, UPPER-CASE names in dialogue, and lines about the player that work for a boy or a girl.
  4. Check: npm test, then walk up to it in the dev scene.

A real pair from Chapter 9. The NPC in thistledown.ts is visible only until its flag is set:

and its script in scripts/ch9.ts plays once, then sets the flag so it never plays again:

Advanced: flags as the story's state machine

Flags default to false and there is no list of them anywhere: a typo (tumbleweed_sen) is a new flag that is never set, and nothing fails until the story hangs. Grep for the flag's other uses before you rely on it, and prefer the chapter's established names (chN_arrived, <thing>_done). The engine sets one family itself: beat_<trainerId> after a won trainer battle. Story progression that gates a key item belongs in the validator's progress gates (PROGRESS_GATES in validate.ts), so the "item before it is needed" proof covers it.

Add a trainer

A trainer is an NPC who battles. The battle data (team, prize, bag, AI, music) lives in src/data/trainers.json, the lines in src/world/trainers.ts; the map only places them. The engine runs the whole encounter: it spots the player in the trainer's line of sight, says the intro, battles, and sets beat_<id> on a win.

stateDiagram-v2
  [*] --> Waiting
  Waiting --> Spotted: player enters the sight line
  Waiting --> Spotted: player talks to them
  Spotted --> Battle: intro line
  Battle --> Beaten: won, sets beat_id, prize, mark if a leader
  Battle --> Waiting: lost, whiteout to the last greenhouse
  Beaten --> Beaten: talk shows the after line
  1. Define it: an entry in trainers.json (in story order; ai is usually basic and music battle_trainer; leave prize out for the top level x 20) and its lines in the chapter's lines record in trainers.ts, under the same id. The Trainer Editor (trainereditor.html) edits the JSON with the same checks.
  2. Place an NPC with trainer: "<id>" and a sight (default 4 tiles) facing an open lane.
  3. Leaders also get mark, usually ai: "smart", items and a balance milestone in balance.test.ts.
  4. Scripted battles (rivals, villains) use { op: "battle", trainer } in a script instead of an NPC trainer.

Advanced: sight lanes, variants and rematches

A trainer who spots the player walks up to them and stays where the battle happened. trainers_block.test.ts simulates every spot each trainer could end up in (one tile short of each cell in its sight line) and fails if that would seal off a warp, trigger, sign or NPC the player could reach from where they were spotted. Give trainers a lane that is open on both sides, or shorten sight.

BRAM's battles exist in three variants, one per starter (rival_5_<line>), and scripts pick one with a byStarter helper that branches on got_starter_* flags. Post-game rematches are clones made by cloneRematch in rematches.ts: id <id>_rematch, every level raised, arrays copied so the first run's team is never shared. A team member marked grafted keeps its level but uses stats from five levels lower (the story's graft collar).

An existing effect kind (flinch, stat, drain…) is data only. Add a ScriptCmd op, end to end

A ScriptCmd op is one instruction in the story language (say, giveItem, warp…). Adding one touches four layers, and the order matters: contract, interpreter, validator, tests.

flowchart LR
  C["1. Contract: add the op to the ScriptCmd union in src/contracts/world.ts"] --> I["2. Interpreter: a case in step() in src/overworld/script.ts"]
  I --> H["ScriptHost method, if the engine must do something"]
  I --> W{"Does the op hold nested command lists?"}
  W -- yes --> WK["3. Walkers: childLists in script.ts, eachCmd in validate.ts, walkScript in src/guide/indexer.ts"]
  W -- no --> V
  WK --> V["4. Validator: a case in checkCmds for every id it names"]
  V --> T["5. Tests: script.test.ts with a fake host, a validator test on a cloned WORLD"]
  1. Contract. Add a member to ScriptCmd in src/contracts/world.ts, with a one-line comment saying what it does.
  2. Interpreter. Add a case to step() in src/overworld/script.ts. Return the promise if the script should wait for it. If it needs the engine (camera, actors, screens), add a method to ScriptHost and implement it in the overworld scene.
  3. Walkers. If the op contains command lists (like if or yesno), every static walker must descend into them, or the validator and the guide silently skip their contents.
  4. Validator. In checkCmds in validate.ts, check every id the op names (species, items, maps, music…).
  5. Tests. A case in script.test.ts runs the op against a fake host and checks its effect; a validator test breaks a cloned WORLD and expects the new error.

How the interpreter dispatches, and what happens to an op it does not know:

async function step(host: ScriptHost, cmd: ScriptCmd, st: ScriptState): Promise<void> {
  const { ctx } = host;
  const flags = ctx.state.flags;
  switch (cmd.op) {
    case "say":
      return ctx.ui.say(cmd.text, cmd.speaker ? { speaker: cmd.speaker } : undefined);
    // …
    case "jingle":
      return ctx.audio.playJingle(cmd.id);
    // …
    case "end":
      throw new ScriptEnd();
    default: {
      // Compile-time exhaustiveness: a new ScriptCmd op without a case fails typecheck here.
      const unknown: never = cmd;
      // Runtime safety net for data the types can't see (the validator rejects it too).
      console.warn(`[script] unknown op "${(unknown as { op?: string }).op}"`);
    }
  }
}
Advanced: what the compiler does and doesn't check

The interpreter is covered: the default branch assigns the command to never, so npm run typecheck fails when you add a member to the union and forget its case in step(). The walkers and the validator are not: childLists and eachCmd fall through for ops they don't list, and the validator's switch has no default at all. Grep for an existing op of the same shape (for a branching op, "ifNurserySeed") and visit every hit. The playthrough's console hook turns the runtime warning into a console.warn issue, so an unhandled op used in the story fails npm run e2e; an op used only in side content will not be caught that way.

An op that awaits something that might never resolve (an animation, a sound) is a soft-lock risk. Give it a bounded duration, and remember the playthrough's watchdog treats an unresolved promise as a lock.

Add a save field, with migration

The save is the GameState object (src/contracts/runtime.ts) wrapped in a versioned envelope ({ v, savedAt, gameId, state }) in localStorage. Players have saves from older builds, so every new field must load sensibly from a save that does not have it.

sequenceDiagram
  participant LS as localStorage
  participant R as createSave().read
  participant M as migrate
  participant N as normalizeState
  participant G as game
  R->>LS: getItem verdant-reach-save
  LS-->>R: JSON text
  R->>M: envelope with v
  M-->>R: same envelope, or null if v is newer than SAVE_VERSION
  R->>N: env.state and a fresh newGameState fallback
  N-->>R: GameState, every field cleaned or defaulted
  R-->>G: CONTINUE

Most fields are additive: the version stays 1, the field is optional or defaulted, and old saves get a safe value. The player's look is the model to copy:

  1. Type. Add the field to GameState, optional if old saves lack it, with a comment saying what an old save means.
  2. New game. Set its starting value in newGameState in src/save/index.ts.
  3. Load. Copy and clean it in normalizeState. Never trust the stored value: validate its type and range.
  4. Test in save.test.ts: a round trip, a save without the field, and a junk value.
// GameState, src/contracts/runtime.ts
/** Chosen at NEW GAME. Optional: saves from before the choice load as "boy". */
playerLook?: PlayerLook;

// newGameState, src/save/index.ts
playerLook: "boy",

// normalizeState, src/save/index.ts
// Additive v1 migration: saves from before the look choice play as the boy.
playerLook: r.playerLook === "girl" ? "girl" : "boy",
const old = fallback() as Partial<GameState>;
delete old.playerLook;
storage.setItem(SAVE_KEY, JSON.stringify({ v: 1, savedAt: 0, gameId: "old", state: old }));
expect(createSave(fallback, storage, fallback).read()!.playerLook).toBe("boy");
const junk = { ...fallback(), playerLook: "plant" } as unknown;
expect(normalizeState(junk, fallback())!.playerLook).toBe("boy");

A change old saves cannot absorb (renaming or restructuring a field) needs a real version bump: raise SAVE_VERSION, change the version: 1 type, and add a step to migrate:

/** Upgrade older envelopes to the current version. */
function migrate(env: SaveEnvelope): SaveEnvelope | null {
  if (typeof env.v !== "number" || env.v > SAVE_VERSION) return null;
  // v1 is the first version; future migrations go here (env.v === 1 -> 2, ...).
  return env;
}
Advanced: the field that silently vanishes

normalizeState builds a new object field by field; it does not spread the stored state. A required field you forget there is a type error, but an optional field is not: the game saves it, and CONTINUE drops it without a word. Always add the round-trip test. Story progress that is just a boolean belongs in flags, which needs no save change at all.

A save from a newer build (v above SAVE_VERSION) is refused rather than half-loaded, so a player who opens an older deploy does not corrupt their file. Keep that rule when you add migrations.

Add a tileset key

A tile key (grass, ice, cable_trunk) names one 16x16 terrain type and its behaviour. Its picture comes from a tileset bundle: a sheet PNG plus a tileset.json that maps keys to cells on the sheet.

flowchart TB
  K["1. TILES in ids.ts: key and TileProps"] --> A["2. optional: AUTOTILE group in constants.ts"]
  K --> L["3. a legend character in build.ts or the map's legend"]
  K --> B["4. art: a cell in some tileset's sheet.png and tileset.json"]
  B --> I["5. npm run art:index if you added files"]
  L --> M["6. use it in a map"]
  I --> T["7. npm test: bundles and validator"]

  1. Key. Add it to TILES in ids.ts with its TileProps: walk, and any of slide, encounter, water, ledge, interact, fieldMove.
  2. Autotiling (optional). If it should join its neighbours (paths, water edges, walls), add it to AUTOTILE in constants.ts, possibly sharing an existing group.
  3. Legend. Give it a character in LEGEND in build.ts, or in one map's own legend.
  4. Art. Add it to exactly one tileset's tiles in public/art/tilesets/<set>/tileset.json (from that set's generator under tools/art/, or by hand), and preview it in the Tile Lab (tilelab.html).

Advanced: behaviour versus looks

Prefer a new key with the same TileProps as the tile it replaces when the change is cosmetic (sign_snow behaves exactly like sign). The environment tests compare roles, so such a swap passes; a key with new behaviour is a gameplay change and needs the validator, the overworld (src/overworld/map.ts) and possibly the guide's map renderer to understand it. A few behaviours are tied to a key's name rather than its props (mat_exit, pit, sign, mailbox), so grep for the name of the tile you imitate.

The game must still run with missing art (it draws a magenta box and logs once), which is why the bundle test, not a crash, is what stops a missing tile from shipping. In the playthrough, that log becomes a missing-asset issue.

Add a page like the guide

The site has several pages built from the same code: the game (index.html), the strategy guide (guide.html) and the Tile Lab (tilelab.html). Each is a separate Vite entry that imports the game's own modules, so its numbers can never drift from the game.

flowchart LR
  HTML["newpage.html at the repo root"] --> MAIN["src/newpage/main.ts"]
  MAIN --> MODS["game modules through their entry points: DATA, WORLD, src/art"]
  CFG["vite.config.ts: build.rolldownOptions.input"] --> HTML
  CFG --> DIST["dist/newpage.html, shared chunks"]
  DIST --> PAGES["deployed with the game"]
  1. HTML. Create <name>.html at the repository root with a mount element and one module script, like guide.html.
  2. Code. Put the page in src/<name>/, with main.ts as its entry and its CSS beside it. Import game modules only through their entry points (DATA from src/data, WORLD from src/world).
  3. Build. Add the page to build.rolldownOptions.input in vite.config.ts. Without this, the page works in npm run dev but is missing from dist/ and the live site.
  4. Test. Keep logic pure and test it next to the code (the guide's indexer.test.ts indexes WORLD without a browser).
  5. Link and document it from the README.

Advanced: what a second page costs the game

Pages share code with the game, so the bundler splits common modules into shared chunks. The game's own entry and behaviour do not change, but a page that imports something heavy only it needs should load it lazily (import()), as the game does for the Tile Lab hook and the dev scenes. A page must never import e2e/ or dev-only modules statically, or they would ship. Use root-absolute paths (/src/…, /favicon.svg) in the HTML only: Vite rewrites those for the relative ./ base, while runtime asset paths stay relative (assets/…) so the site works under /verdant-reach/.
