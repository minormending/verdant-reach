The fixed-step loop

A fixed-step loop advances the game in equal slices of time (here 1000/60 ms, one step) no matter how fast the display refreshes. Real elapsed time goes into an accumulator; while it holds at least one step, the loop runs one update and subtracts a step. Drawing happens once per animation frame. The result: a 60 Hz, 120 Hz or 144 Hz monitor all play at the same speed, and every animation, text speed and timer can be counted in steps ("frames" in the code). 

flowchart TB
  raf["requestAnimationFrame(now) or setTimeout under ?timer"] --> acc["acc += min(250, now - last)"]
  acc --> fast{"dev ?speed above 1?"}
  fast -->|yes| batch["run update() speed times, acc = 0"]
  fast -->|no| check{"acc holds a whole step?"}
  check -->|yes| upd["update(): poll, top.update, endFrame, onTick"]
  upd --> sub["acc -= step"] --> check
  check -->|no| draw["find lowest scene to draw (skip transparent), clear to black, draw upwards"]
  batch --> draw
  draw --> again["schedule(frame)"]

From core.ts:

  let acc = 0;
  let last = performance.now();
  const update = () => {
    input.poll();
    scenes.top()?.update(step);
    input.endFrame();
    onTick(step);
  };
  const frame = (now: number) => {
    acc += Math.min(250, now - last);
    last = now;
    // Preserve the normal accumulator exactly at speed 1. Accelerated dev
    // frames run a fixed batch, with input edges consumed after each step.
    if (speed > 1) {
      for (let i = 0; i < speed; i++) update();
      acc = 0;
    } else {
      while (acc >= step) {
        update();
        acc -= step;
      }
    }
    const all = scenes.all();
    let from = all.length - 1;
    while (from > 0 && all[from].transparent) from--;
    g.fillStyle = "#000";
    g.fillRect(0, 0, SCREEN_W, SCREEN_H);
    for (let i = Math.max(0, from); i < all.length; i++) all[i].draw(g);
    schedule(frame);
  };
  • Order inside one step: read controllers (poll), update the top scene, clear this step's press edges (endFrame), then the tick callback (play time, the error screen's tick count).
  • ?speed=N (dev only, 1–16) runs exactly N steps per drawn frame and ignores the clock; the e2e runner uses speed 8.
  • ?timer schedules frames with setTimeout(…, 1000 / FPS), because browsers throttle requestAnimationFrame in hidden or embedded panes.
Advanced: invariants, performance and failure modes
  • The 250 ms clamp caps catch-up at 15 steps per frame. After a stall (a GC pause, a tab coming back) the game slows briefly instead of fast-forwarding through seconds of gameplay or spiralling (updates taking longer than the time they simulate).
  • dt is always the constant step. Scenes receive update(step) and most ignore it, counting frames instead. Never multiply by wall-clock deltas in game logic: it breaks determinism under ?seed and ?speed.
  • Speed batching ignores refresh rate. ?speed=8 on a 120 Hz display is 16× real time. That is fine for e2e (Chromium headless) but don't use it to judge feel.
  • Draw is once per frame, update can be zero times. On a 120 Hz screen about every other frame draws without an update, so draw must be pure: no state changes, no randomness. Code that animates "per draw" will run at different speeds on different monitors (the screens kit counts updates for this reason).
  • Exceptions kill the loop. schedule(frame) is the last line, so a throw in any update or draw stops rescheduling. The error screen notices that ticks stopped and shows the card (errors).
  • Input edges at speed > 1 are consumed after each batched step, so a single key press is seen by exactly one update, as at speed 1.

Input: keyboard, touch and gamepads

The game has eight buttons, the Game Boy's: up, down, left, right, a, b, start, select (Button in ids.ts). Everything a player can press becomes one of these. Three sources feed them, and the game cannot tell them apart:

  kb["physical keyboard"] -->|"keydown / keyup (e.code)"| km["KEYMAP"]
  touch["on-screen controls (platform/touch.ts)"] -->|"sendKey: synthetic KeyboardEvent"| km
  km --> keys["keys: Set of Button"]
  pads["navigator.getGamepads()"] --> prof["profileFor(pad): STANDARD, 8BitDo raw, generic raw"]
  prof --> pb["padButtons(pad)"] -->|"poll() each step"| pad["pad: Set of Button"]
  keys --> edges["down (press edges) + holdFrames"]
  pad --> edges
  edges --> api["Input: pressed, held, repeat"]
  api --> scene["top scene update()"]
  km -. "first key" .-> unlock["audio.unlock()"]
  pb -. "every new pad press" .-> unlock

The keyboard map, also read by the guide's controls table (core.ts):

  ArrowUp: "up", ArrowDown: "down", ArrowLeft: "left", ArrowRight: "right",
  KeyW: "up", KeyS: "down", KeyA: "left", KeyD: "right",
  KeyZ: "a", Space: "a", KeyJ: "a",

  Enter: "start", ShiftLeft: "select", ShiftRight: "select",

The three questions a scene can ask:

MethodTrue whenUse it for
pressed(b)The button went down during this step (an edge)Confirming, cancelling, opening a menu
held(b)The button is down on the keyboard or any padWalking, running with B, fast text
repeat(b)On the press, then every 6 steps once held more than 18 stepsMenu cursors that auto-repeat

In numbers: holdFrames grows by one in every endFrame, and repeat returns true when n > 18 && n % 6 === 0, so the first repeat fires 24 steps (0.4 s) after the press, then 10 times a second.

Gamepads

gamepad.ts maps buttons by position, Game Boy style: the right face button is A, the bottom one is B. On Nintendo-layout pads (8BitDo, Switch Pro) the labels match; on an Xbox-layout pad, A is the button marked B. Browsers report a pad either with the W3C "standard" mapping or raw (""), so profileFor picks one of three profiles: 

/** W3C standard mapping: 0 bottom, 1 right, 2 left, 3 top, 8 back, 9 start, 12-15 D-pad. */
const STANDARD: Profile = {
  buttons: { 1: "a", 3: "a", 0: "b", 2: "b", 8: "select", 9: "start", 12: "up", 13: "down", 14: "left", 15: "right" },
  stick: [0, 1],
};

/** 8BitDo pads in D-input mode (vendor 2dc8): the D-pad is axes 0/1. */
const EIGHTBITDO_RAW: Profile = {
  buttons: { 0: "a", 4: "a", 1: "b", 3: "b", 10: "select", 11: "start" },
  stick: [0, 1],
};

/** Unknown raw pads: the usual DirectInput order. */
const GENERIC_RAW: Profile = {
  buttons: { 0: "a", 1: "b", 8: "select", 9: "start" },
  stick: [0, 1],
};

readGamepads() unions every connected pad, so two controllers work at once, and returns an empty set where the API is missing (tests, old browsers). PAD_LABELS provides the help-text names ("A (right face button)").

Advanced: input edge cases and how to extend
  • No double presses across sources. A press only becomes an edge if the button wasn't already held by the other source (isHeld checks keys and pads), so holding Z and pressing the pad's A doesn't press twice.
  • OS key repeat is ignored for edges: a repeated keydown finds the button already held. Menu repeat is the engine's own repeat(), which is frame-counted and therefore identical on every machine.
  • Blur clears the keyboard (keys.clear(), holdFrames.clear()), because a keyup that happens while another window has focus never arrives. Pads need no such fix: they are re-read every step.
  • Only mapped keys call preventDefault, so browser shortcuts keep working, and the shell's F (fullscreen) is not a game button.
  • Polling is per step, not per frame, so a pad press shorter than one step (16.7 ms) can be missed; that is below what a human produces.
  • Adding a controller profile: add a Profile, a matcher in profileFor (before the generic fallback), and cases in gamepad.test.ts; padButtons takes a plain PadState, so tests need no browser. createInput also accepts a readPads function for the same reason.
  • Hat switches: Chrome reports some DirectInput hats as one axis in eight steps from -1 (up) clockwise; values beyond ±1.05 mean centred. hatDirections turns that into one or two directions.

Loading assets

Code never loads files directly. It asks for a logical asset path built by a helper in constants.ts, such as speciesPath("oak_acorn", "front") → assets/species/oak_acorn/front.png, and the art registry (src/art/registry.ts, returned by createAssets()) resolves it to a file in a swappable bundle under public/art/, applying any active art packs, sheet cells and sport palettes. Details of the format are in docs/ART.md; this is the engine's view of it. 

flowchart TB
  call["assets.image(logical path)"] --> ready{"registry ready (index.json + bundle JSON loaded)?"}
  ready -->|no| kick["start ready(), return undefined"]
  ready -->|yes| cache{"derived image cached?"}
  cache -->|yes| hit["return canvas or image"]
  cache -->|no| res{"catalog.resolve(path)"}
  res -->|"no bundle provides it"| none["return undefined (isMissing = true)"]
  res -->|"file URL"| file{"file loaded?"}
  file -->|no| lazy["loadFile(url) in background, return undefined"]
  file -->|yes| derive["cut sheet cell / recolour sport, cache, return"]
MethodMeaning
image(path)The image if ready; otherwise undefined and a lazy load starts
has(path)Loaded and ready to draw now
exists(path)Some bundle provides it, loaded or not, and it hasn't failed
isMissing(path)Known not to resolve, or its file failed (engine extension, EngineAssets)
loadAll(paths?, onProgress?)Preload; with no paths, everything the registry provides (what boot does)
speciesAnim(id)The species bundle's anim after packs are applied

Packs come from ?art=a,b (which wins, even when empty) or else localStorage key verdant.artPacks.

Advanced: what can go wrong
  • image() can return undefined on any call, even after boot (a newly enabled pack, a lab override). Draw code must tolerate it: drawImagePath draws nothing while loading and the magenta box only once the file is known missing.
  • A missing index.json is not fatal: the registry warns and treats every assets/ path as a legacy file. An un-indexed new PNG is silently absent until npm run art:index; the bundle tests catch required frames.
  • Derived images are cached per logical path and the cache is cleared on every rebuild() (pack switch, override). Holding on to a returned canvas across a pack switch draws stale art.
  • Fetches use cache: "no-cache" for JSON, so art edits show up on reload without hashed filenames.

Drawing helpers

gfx.ts collects the helpers most scenes share:

  • drawImagePath(g, assets, path, sx, sy, sw, sh, dx, dy, dw?, dh?) draws part of an image at rounded integer coordinates and returns false when it isn't available. drawMissing draws the magenta-and-purple checker and logs the path once.
  • Timers.frames(n) returns a promise that resolves after n calls to tick(): "wait 20 frames" in a cut-scene.
  • Fader animates a full-screen black or white overlay; to(target, frames) returns a promise. It quantises into four steps like a GBC palette fade:
  draw(g: CanvasRenderingContext2D, w: number, h: number) {
    if (this.level <= 0) return;
    // Quantise into 4 steps like a GBC palette fade.
    const steps = Math.ceil(this.level * 4) / 4;
    g.globalAlpha = steps;
    g.fillStyle = this.color === "black" ? "#000000" : "#f8f8f8";
    g.fillRect(0, 0, w, h);
    g.globalAlpha = 1;
  }
  • Shaker gives a short screen shake as { x, y } offsets per frame.
Advanced: frame-driven promises
  • Someone must tick them. Timers, Fader and Shaker only advance when the owning scene calls tick() in its update. Because only the top scene updates, a cut-scene paused under the PAUSED overlay (or a text box) stops exactly where it is. That is the design, not a bug.
  • Fader.to resolves the previous pending fade immediately when a new one starts, so overlapping fades never leave an awaiter hanging. Switching colour mid-fade restarts from clear.
  • Timers.frames(0) resolves at once; fractional counts are rounded.

Time of day

As in Crystal, time of day comes from the player's real clock: TIME_OF_DAY in constants.ts is { morningStart: 4, dayStart: 10, nightStart: 18 }, and timeOfDayFor(hour) in context.ts maps an hour to "morning" | "day" | "night". ?time=morning|day|night overrides it. 

stateDiagram-v2
  direction LR
  night --> morning: hour 4
  morning --> day: hour 10
  day --> night: hour 18

A map can force its own time (MapDef.time, for example the Prologue's night on the Herbarium roof). Anything that happens on a map (tint and lights, encounters, ifTime in scripts, music, battle backdrops, growth) should use time.ts: 

/** The time of day on a map: its forced `time`, else the clock. */
export function mapTime(def: Pick<MapDef, "time"> | undefined, clock: () => TimeOfDay): TimeOfDay {
  return def?.time ?? clock();
}

/** The time of day where the player is standing. */
export function worldTime(ctx: Pick<GameContext, "world" | "state" | "timeOfDay">): TimeOfDay {
  const id = ctx.state?.position?.map;
  return mapTime(id ? ctx.world?.maps?.[id] : undefined, () => ctx.timeOfDay());
}
Advanced: clock subtleties
  • ctx.timeOfDay() reads the clock on every call, so crossing 18:00 mid-session changes encounters and tint at the next check. The ?time override is read once, when the context is created.
  • ?time works in production (unlike ?seed), so it is safe to give players and testers.
  • The ambience bed has its own clock: clockTimeOfDay() in audio/ambience.ts repeats the same thresholds and override but does not see MapDef.time. A forced-night map gets night ambience only if its music implies it (as prologue_bloom does). If you change the thresholds, change both.
  • Calendar days (berry regrowth in harvested, wanderer recovery) are stored as local YYYY-MM-DD strings, separate from time of day.

Seeded randomness

Normally the game uses Math.random. For reproducible runs, dev builds accept ?seed=N (an unsigned 32-bit integer). A seed does not just seed one generator: it creates several random streams, each derived from the seed and a name, so that drawing a particle can never change a critical hit. random.ts in full: 

import { seeded, type Rng } from "../battle/logic/rng";

/** URL seeds are unsigned 32-bit integers, and never apply to production. */
export function devSeed(): number | null {
  if (!import.meta.env.DEV || typeof location === "undefined") return null;
  const value = new URLSearchParams(location.search).get("seed");
  if (value === null || !/^\d+$/.test(value)) return null;
  const seed = Number(value);
  return Number.isInteger(seed) && seed >= 0 && seed <= 0xffffffff ? seed : null;
}

/** Stable independent streams: cosmetic/NPC draws cannot shift battle rolls. */
export function randomStream(seed: number, name: string): Rng {
  let hash = seed >>> 0;
  for (const char of name) hash = Math.imul(hash ^ char.charCodeAt(0), 16777619) >>> 0;
  return seeded(hash);
}

/** Covers legacy direct draws (save ids, dev battles, particles and audio).
 * Keep these separate from ctx.rng so drawing a particle cannot change a crit. */
export function installDevRandom(): void {
  const seed = devSeed();
  if (seed !== null) Math.random = randomStream(seed, "direct");
}
flowchart TB
  seed["?seed=N (dev only)"] --> h["randomStream(seed, name): FNV-style hash of name, then mulberry32"]
  h --> direct["'direct': replaces Math.random (particles, audio, save ids)"]
  h --> world["'world': ctx.rng (overworld: encounters, NPCs)"]
  h --> bt["'battle:trainer:ID' per trainer"]
  h --> bw["'battle:wild:SPECIES:LEVEL' per wild opponent"]
  bt --> battle["createBattleScene with ctx plus that rng"]
  bw --> battle

Battle streams are created on first use and kept in a Map, so a rematch with the same trainer continues that trainer's stream. The e2e runner defaults to --seed 1 and records the seed in its report; npm run e2e -- --seed 42 replays another one.

Advanced: determinism trade-offs
  • Why streams: with one shared generator, any extra draw (an NPC idling a frame longer, a new particle effect) shifts every later battle roll, and a seeded e2e failure stops reproducing after an unrelated change. Named streams isolate battles from the overworld, and each opponent from the others.
  • Remaining coupling: within the "world" stream, encounter rolls still depend on how many draws came before, and the overworld's NPC, pet and bird AI draw from that same stream every step, so the wild encounter you get depends on timing. Only the battle itself is isolated. A wild battle's stream is keyed by species and level, so two different encounters with the same species and level share a stream.
  • Production ignores the seed (import.meta.env.DEV is false), so a seed in a live URL does nothing. Without a seed, ctx.rng is Math.random.
  • Adding a stream: call randomStream(seed, "your-name") once and pass the Rng down; pure logic should take an Rng parameter (as all of battle/logic does) so tests can use seeded() or sequence().
  • Cries are deterministic too, but independently: audio/cry.ts has its own copy of the string hash and mulberry32, seeded by the line and species id, so a species always sounds the same with or without ?seed.
