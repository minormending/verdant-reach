The other pages

The site serves more than the game. Beside index.html there are pages that import the game's own TypeScript modules and draw from them:

PageCodeFor
guide.html, the guidebooksrc/guide/Players: a strategy guide with a walkthrough, map panels, bosses and the Herbarium
tilelab.html, the Tile Labsrc/tilelab/Artists: every map under the current tiles, tileset swaps, export as an art pack
devdocs.html, these docssrc/devdocs/Developers: this page, assembled from HTML fragments, with charts drawn from the game's data

Why build them from the game's code instead of writing them separately? Because then they can't drift. A level, an encounter rate or a tile in the guide is computed from the same WORLD, DATA and art registry the game runs on. Change a trainer's team and the guide changes with it. There is no export step to forget.

One Vite build, several pages

Vite builds a multi-page app when build.rolldownOptions.input names more than one HTML file. Each HTML file is an entry; its <script type="module" src="…"> is where the bundler starts following imports. From vite.config.ts:

export default defineConfig(({ command }) => ({
  base: command === "build" ? "./" : "/",
  build: {
    rolldownOptions: {
      input: {
        main: fileURLToPath(new URL("./index.html", import.meta.url)),
        guide: fileURLToPath(new URL("./guide.html", import.meta.url)),
        tilelab: fileURLToPath(new URL("./tilelab.html", import.meta.url)),
      },
    },
  },
}));

npm run build then emits dist/index.html, dist/guide.html and dist/tilelab.html side by side. The developer docs page joins this list as one more entry. The base is relative (./), so every page works from the GitHub Pages subpath.

When two entries import the same module, the bundler doesn't copy it into both. It moves the shared code into a shared chunk, a separate JS file that both pages load. The browser caches it, so opening the guide after playing doesn't download src/world again.

The rule: the game must not depend on these pages

The game must behave exactly the same whether or not any of these pages' code is loaded. Sharing goes one way: pages import game modules; game modules never import page modules. The single exception is opt-in and lazy:

// ?tilelab=1 (the Tile Lab's "Walk around" button): apply its saved tile
// overrides in memory. Without the param this module is never loaded.
if (new URLSearchParams(location.search).has("tilelab")) await (await import("./tilelab/hook")).applyStoredTileLab();

  B["boot(): createAssets()"] --> L["assets.loadAll()"]

  Q -->|"no"| F["loading.finish()"]
  Q -->|"yes"| I["import('./tilelab/hook')"]

Never add a static import from src/guide, src/tilelab or src/devdocs to game code. It would pull page code (and its CSS) into the game bundle, and a bug on a page could then break the game. If a page needs something from the game, move it into a game module and import it from there.
Advanced: how the boundaries are enforced, and what to watch
  • Dynamic imports are separate chunks. import("./tilelab/hook") and import.meta.glob("./*/dev.ts") (non-eager) each become a chunk fetched only when that code path runs. Run grep -rn "guide/\|tilelab/\|devdocs/" src outside those folders: the only hit should be the hook line in src/main.ts.
  • Dev-only code is removed in production. Branches guarded by import.meta.env.DEV, such as guide.html?preview=atlas and the docs' ?fixture=1, are dead code in a production build (the Tile Lab's "Walk here" button is hidden there too).
  • Pure modules make sharing safe. ArtCatalog, indexer.ts, plan.ts and pack.ts touch no DOM and have no side effects at import time. A page can import them without starting anything. Watch for module-level side effects (a top-level addEventListener, a registry created on import) when you share a new module.
  • Separate storage keys. Each page keeps its own preferences (verdant.guide.theme, verdant.tilelab.theme, verdant.tilelab.tab). The one shared key is verdant.artPacks, deliberately, so a pack switched on in the Art Lab also shows in the guide.
  • The guide and the Tile Lab each create their own art registry with createArtAssets(). Pages share code, never in-memory state.

The walkthrough content contract

A section is { id, part, title, blocks }. Sections with the same part ("Prologue", "Chapter 3") are grouped under one heading. Blocks are a discriminated union: the key that is present decides how the block renders.

export type Block =
  /** A paragraph. Inline: **bold**; UPPER-CASE names as in the game. */
  | { p: string }
  /** A boxed hint (puzzle solutions, missables, strategy). */
  | { tip: string; title?: string }
  /** A bullet list. */
  | { list: string[] }
  /** "Before you leave" checklist. */
  | { checklist: string[] }
  // …
  | { map: MapId; flags?: Record<string, boolean>; note?: string }
  /** A boss card (leader, rival, admin, Council): portrait, full team with levels and moves, prize. */
  | { boss: string; note?: string }
  /** A highlighted creature (a gift, starter, legendary): sprite, types, stats and where to get it. */
  | { species: SpeciesId; note?: string }
  /** A highlighted key item (field tools such as the lantern or raft). */
  | { item: ItemId; note?: string };
Never type a level, rate, team or price into a p block. Put a { map }, { boss }, { species } or { item } block where the reader needs it, and the number stays right forever.

The indexer

mapFinds(world, data, id) collects everything a map panel shows: wild encounters per method (grass, bog, water) with day and night percentages and every encountersWhen variant, items on the ground, hidden items and berry bushes, trainers, and everything the map's scripts give, sell, trade or fight. Script effects are found by walking the scripts, following call and every branch:

/** Every op reachable from a script (following `call`s and every branch). */
export function walkScript(
  world: Pick<WorldData, "scripts">, scriptId: string, visit: (op: ScriptCmd, when: string[], scriptId: string) => void,
  ctx: LabelContext = {},
): void {
  const seen = new Set<string>();
  const run = (id: string, when: string[]) => {
    if (seen.has(id)) return;
    seen.add(id);
    // …
        if (op.op === "call") run(op.script, w);
        for (const b of branches(op, ctx)) if (b.cmds.length) walk(b.cmds, b.label ? [...w, b.label] : w);
    // …
  };
  run(scriptId, []);
}

The when list is how the guide labels conditional finds: an item given only after a flag is set is listed with that condition.

The coverage test

walkthrough.test.ts keeps the guide honest. It checks that section ids are unique and well formed, that every block names a map, trainer, species or item that exists, that text blocks aren't empty, and that every map with wild plants, trainers or items has a map panel somewhere:

/** Maps with encounters, trainers or items that no walkthrough `map` block shows. */
export function uncoveredMaps(sections: Section[]): string[] {
  const covered = new Set(blocks(sections).flatMap(({ b }) => ("map" in b ? [b.map] : [])));
  return allMapFinds(WORLD, DATA).filter((f) => mapHasContent(f) && !covered.has(f.map)).map((f) => f.map);
}

So adding a new route with trainers fails npm test until someone writes its walkthrough section. A sanity test also checks that, with an empty walkthrough, more than 40 maps would be uncovered, so the rule can't silently pass by matching nothing.

Advanced: story state, rendering and dev previews
  • Unset flags read false, as in a new game. { map: "route_9", flags: { game_cleared: true } } applies legendWhen, NPC visibleWhen and the active encounter table for that state. Trainers and item balls still show unless flags names their condition, because they are the guide's subjects.
  • The map picture is the game's renderer, not a copy. renderMap calls buildMap, refreshLegend, autotileMask, drawCell, drawStructure and drawCharacter from src/overworld, Y-sorted as in the game. A rendering bug in the guide is usually a bug in the game.
  • Lazy and printable. Pictures render when scrolled within 800px. renderAllPending() draws the rest before print(), and beforeprint opens every <details>.
  • Pictures as URLs. artUrl() returns the bundle file itself when no cutting or recolouring is needed (lazy-loadable, printable), else a data URL of the registry's cut canvas.
  • guide.html?preview=atlas (dev only) appends a stand-in part with a panel for every map and a sample of every block type, which is useful while writing.

The Tile Lab (tilelab.html)

The Tile Lab is for trying tileset swaps on the whole world before committing to them. Everything lives in memory and in IndexedDB. Nothing is written to public/art/ until you install an export by hand.

  • The atlas (atlas.ts) draws every map with the guide's renderMap, lazily as cards scroll into view. Click a card for a large view with zoom, pan and hover names. Hold to compare (or hold C) shows the art without the lab's changes.
  • The Tiles tab shows every TileKey, grouped by its owning tileset, with its usage (usage.ts: map rows, legend, legendWhen, the border, field-move results).
  • The Tilesets tab previews installed packs, replaces whole sheets, and maps an external sheet.

When several apply to one key, the order is: a single-tile swap, then the mapping, then a replaced sheet, then the current art. In code, effectiveEdits() lays the single-tile edits over the mapping's edits, and planTileset() applies the result over art cut from the replaced sheet.

The key design decision: a TilesetPlan is an art-pack tileset in the format of art packs. The in-browser preview and the exported pack are the same data, so what you see in the lab is what you get after installing.

How a plan reaches the registry

export async function installLab(reg: ArtRegistry, state: LabState): Promise<Installed> {
  await reg.ready();
  reg.clearOverrides();
  const packs = state.packs.filter((p) => reg.index.packs[p]);
  if (packs.join(",") !== reg.activePacks().join(",")) reg.setActivePacks(packs);
  const base = reg.fork(reg.activePacks());
  await base.loadAll(pathsToLoad(base.catalog, state));
  const plans = planAll(registrySource(base), state);
  for (const p of plans) {
    const v = reg.bundle("tilesets", p.id);
    if (!v) continue;
    reg.overrideFile(v.layers[0].dir + LAB_SHEET, rgbaToCanvas(p.sheet));
    reg.patchBundle("tilesets", p.id, { ...p.json, sheet: LAB_SHEET });
  }
  return { plans, base };
}

Each touched tileset gets a lab-layer JSON patch whose sheet is tilelab-sheet.png, a file that exists only as an in-memory override. The base fork, with the same packs and no edits, is the "before" side of hold-to-compare.

Export and the game hook

Export writes <id>.zip: a README.md, the pack folder (<id>/pack.json, tilesets/<tileset>/tileset.json and sheet.png), per-tile PNGs named the way art.py explode names them (so you can bake them into the base with art.py pack), and the mapping JSON, if any. Before writing, the pack is checked with src/art/validate.ts, the same rules as npm test.

Advanced: the in-memory sheet trick, sparse versus full plans, and failure modes
  • Why the in-memory sheet resolves. The lab-layer patch defines tiles, so for edited keys the defining layer is @lab. findFile skips the lab layer and finds tilelab-sheet.png in no index listing, so it returns the base folder's URL with listed: false. installLab registered its override at exactly that URL (v.layers[0].dir + LAB_SHEET), and fileNow(url) checks overrides first. No resolver change was needed.
  • Sparse versus full. With single-tile edits only, the plan's sheet holds just the edited keys' images (deduplicated by CellPacker) and tiles names only those keys, with their untouched alts and masks copied in, because a pack's tiles.<key> replaces the whole key. With a replaced sheet, tiles names every key of the tileset and edited keys go in extra rows below, because a layer that defines tiles reads its own sheet.
  • A dependency-free ZIP. zip.ts writes store-only ZIPs (CRC-32, no compression, no ZIP64) and stored-block zlib streams, so PNGs can be encoded without a compressor. That keeps the zero-runtime-dependencies rule.
  • Storage can fail. Every IndexedDB call in store.ts resolves rather than throws. Without IndexedDB (private windows, blocked storage) the lab still works but forgets on reload. In the game, applyStoredTileLab() catches everything and carries on with the normal art.
  • Limits. Thumbnails are smoothly downscaled; the large view is pixel-exact. Maps draw frame 1 of animated tiles. Structures, characters and species are out of scope (use the Art Lab).

These developer docs (devdocs.html)

This page follows the same pattern. Writers only write HTML fragments in src/devdocs/sections/ (10-art.html, 11-pages.html…), following src/devdocs/CONTRACT.md. The shell loads them in file-name order, builds the navigation, renders the Mermaid diagrams, highlights code and draws the charts from the game's own modules, so a chart such as bundle-kinds always reflects the current build.

Advanced: validating fragments
  • src/devdocs/validate.ts scans fragments as plain strings (no DOM), so the same checks can run in the browser and in Vitest. It rejects elements outside an allow-list (an unknown tag is usually an unescaped < in a code block, like Array<string>), forbids scripts, styles and form controls, checks ids, and reports # links that point nowhere across all fragments.
  • Chart names come from CHART_NAMES in names.ts, which deliberately imports nothing from the game so the validator stays cheap. Use only names from that list.
