Saving and loading

Everything the game needs to resume lives in one object, GameState (contracts/runtime.ts), held at ctx.state. Saving writes it to the browser's localStorage; loading reads it back, repairs anything missing or damaged, and hands it to the overworld. The code is all in src/save/index.ts, about 300 lines, and has no DOM dependencies beyond the storage object, which tests replace with an in-memory fake.

The guiding rule: a save from any earlier build must always load. Players don't re-download a save file; it simply sits in their browser while the game updates under it on every push to main.

The save format and envelope

A save is a save envelope: the state, wrapped with a format version, a timestamp and a game id. It is stored as JSON under one key. Options are also stored on their own under a second key, so they survive NEW GAME and apply on the title screen.

export const SAVE_KEY = "verdant-reach-save";
export const OPTIONS_KEY = "verdant-reach-options";
export const SAVE_VERSION = 1;

export interface SaveEnvelope {
  v: number;
  savedAt: number;      // epoch ms
  gameId: string;       // distinguishes "another save file" on overwrite
  state: GameState;
}

  • v is the envelope version. It has been 1 since the first save; changes so far have all been additive (see migrations).
  • gameId is a random id made when a game starts (beginNewGameSession). If you start a NEW GAME and then save over a file from a different game, the ids differ and the game asks "There is already a save file. Is it OK to overwrite?".
  • There is exactly one save slot.
Advanced: the game id's life cycle
  • A fresh id is made when the module loads and again by beginNewGameSession() at NEW GAME.
  • read() adopts the envelope's id, so after CONTINUE your next save matches and doesn't ask to overwrite your own game.
  • The check compares ids only; it says nothing about which save is "newer". The SAVE window shows the stored file's summary so the player can decide.

What is not saved is just as deliberate: boulder positions (puzzles reset on entry), hideNpc overrides, the camera, and which wild plant you were about to meet. Anything that must survive a reload has to be a flag or a field here.
Advanced: shape choices in GameState
  • version: 1 is a literal type, so code can't accidentally write another number into the state; the real format version lives on the envelope.
  • Records (bag, flags, harvested) rather than arrays keep JSON small and lookups O(1), and make "missing" mean "zero" or "false" for free.
  • Some things are derived rather than stored (quest step ticks, which towns SEED GLIDE offers, a Wanderer's max HP), so they can't disagree with the data after a change. Party members do store their computed stats, which the battle code keeps current.
  • Optional fields (hallOfFame, nursery, rafting, burrHitch, trainerRematches) are only added by normalizeState when the stored value is present and valid, so an old save never gains, say, an empty Hall of Fame that would read as a clear.

Writing and reading

createSave(getState, storage, fallback) returns the save service that the engine puts on ctx.save. write() wraps the current state in an envelope, stores it and returns true only if it reads back; read() unwraps, migrates and normalises.

return {
  write() {
    const state = getState();
    const env: SaveEnvelope = { v: SAVE_VERSION, savedAt: Date.now(), gameId: currentGameId, state };
    if (!storage) {
      console.error("[save] write failed: no storage available");
      return false;
    }
    try {
      const json = JSON.stringify(env);
      storage.setItem(SAVE_KEY, json);
      if (storage.getItem(SAVE_KEY) !== json) throw new Error("the stored save does not read back");
    } catch (e) {
      console.error("[save] write failed", e);
      return false;
    }
    storeOptions(state.options, storage);
    return true;
  },
  read() {
    const env = readEnvelope();
    if (!env) return null;
    const state = normalizeState(env.state, fallback());
    if (state) currentGameId = env.gameId ?? currentGameId;
    return state;
  },
  exists: () => readEnvelope() !== null,
  clear: () => storage?.removeItem(SAVE_KEY),
  // …
};

The only way a player saves is START, then SAVE (and the old end-of-slice offer). Both go through saveDialog() in ui/widgets.ts. There is no autosave.

Migrations: old saves get defaults

Verdant Reach migrates additively. Instead of bumping the version and writing a converter for each change, every field added since version 1 is either optional in the type or given a default by normalizeState(). Old saves simply lack the field and get the default; new saves carry it. The version stays 1.

The boy/girl choice is the cleanest example. Saves from before the choice have no playerLook, and they must keep playing as the boy they always were:

return {
  version: 1,
  playerName: typeof r.playerName === "string" && r.playerName ? r.playerName : DEFAULT_PLAYER_NAME,
  // Additive v1 migration: saves from before the look choice play as the boy.
  playerLook: r.playerLook === "girl" ? "girl" : "boy",
  rivalName: typeof r.rivalName === "string" && r.rivalName ? r.rivalName : DEFAULT_RIVAL_NAME,
  money: typeof r.money === "number" && isFinite(r.money) ? Math.max(0, Math.floor(r.money)) : fallback.money,
  party: cleanSeeds(arr(r.party, []).slice(0, 6)),
  ...(hallOfFame !== undefined ? { hallOfFame } : {}),
  // …
  harvested: cleanHarvested(r.harvested) ?? {},
  ...(r.nursery !== undefined && cleanNursery(r.nursery) ? { nursery: cleanNursery(r.nursery) } : {}),
};

Notice the pattern: compare against the one value that means "new behaviour" (=== "girl"), so missing, misspelled and hand-edited values all fall back to the old behaviour. Read sites agree: playerArt(state) in constants.ts also treats anything but "girl" as the boy.

Bigger structures get a dedicated cleaner: cleanNursery, cleanSeeds, cleanHarvested, cleanHallOfFame, cleanWanderers, cleanTrainerRematches. Each keeps what is well formed and replaces the rest with fresh values.

migrate() is where a real version change would go. Today it only rejects envelopes it can't understand:

/** Upgrade older envelopes to the current version. */
function migrate(env: SaveEnvelope): SaveEnvelope | null {
  if (typeof env.v !== "number" || env.v > SAVE_VERSION) return null;
  // v1 is the first version; future migrations go here (env.v === 1 -> 2, ...).
  return env;
}
Advanced: when an additive migration is not enough
  • Renaming or removing a field (or a flag, an item id, a map id) breaks old saves silently: the old value is still in storage under the old name. Either keep reading the old name in normalizeState, or bump SAVE_VERSION and convert in migrate(), with a test that loads a literal old envelope.
  • Map ids are load-bearing. normalizeState rejects a save whose position.map isn't in MAP_IDS. Renaming a map strands every save made on it.
  • Defaults must be honest. cleanHallOfFame never invents a clear, and cleanWanderers gives old saves healthy, unreleased Wanderers (release still needs the story flags). A default should describe what an old player actually did.
  • Normalise at the boundary only. The rest of the game trusts ctx.state to be well formed. Party members themselves are not deeply validated (only their seed countdowns), because only the game writes them.
  • Envelope metadata is read raw. meta() reads the envelope without normalising, so the CONTINUE window shows exactly what is stored (an empty name stays empty there, though the loaded game uses SORREL).

Storage and failure handling

Browser storage can be missing (some private modes, sandboxed frames), full, or hold junk. Each case has a defined outcome:

SituationWhat happens
Accessing localStorage throwsdefaultStorage() returns null; every read finds no save; write() logs and returns false, and the dialog says "The save failed! Browser storage may be full or off."
setItem throws (quota), or the save doesn't read backwrite() catches it, logs [save] write failed and returns false; the dialog shows the same failure line. write() never throws.
Stored text isn't JSONreadEnvelope warns and returns null: treated as no save.
Envelope from a newer build (v > 1)Treated as no save.
Position on an unknown mapread() returns null.
Options unreadableIgnored; text speed falls back to "mid".
Advanced: failure modes worth knowing before you touch this
  • No false success. "saved the game" (and the save sound) only follow a write() that returned true. Every save goes through saveDialog, so a new place that saves should call it, or at least check write()'s result, rather than assume the write landed. Options written to OPTIONS_KEY stay best-effort and silent.
  • CONTINUE can show and then do nothing. The title decides to show CONTINUE from meta(), which only needs a readable envelope. If normalizeState then rejects it (unknown map), continueGame quietly returns to the menu.
  • A newer save can be overwritten without warning. envelope() returns null for v > SAVE_VERSION, so the overwrite prompt (which compares game ids) never fires. Only matters if a build with a higher version ships and is then rolled back.
  • Options have two homes. They are written into the save and to OPTIONS_KEY. On CONTINUE the title replaces the save's copy with loadOptions(), so the most recent options win, even if they were changed on the title screen of another game.
  • Size. The state is small (well under a megabyte even with a full box), far below typical quotas; flags grow by one entry per story beat and per cleared field cell.

Two details from the overworld make CONTINUE safe:

  • Boulder rooms. Boulders reset when a map loads, so standing where you saved might now be behind a stone. continuePosition() (continue.ts) moves you to the room's entrance instead.
  • onEnter runs. Unlike a NEW GAME, CONTINUE runs the map's onEnter after the fade-in, so map scripts must be safe to run again (the once-only flag pattern in Scripts).

The raft and BURR's hitch survive CONTINUE on purpose: loadMap keeps rafting on the first load, and burrHitch is only cleared on the next real map change.

Advanced: CONTINUE invariants
  • continuePosition() throws if a boulder room's first exit map has no warp back into it. That would be a world bug; uproot.test.ts calls it for every boulder room so a bad room fails in CI, not at a player's CONTINUE.
  • The overworld's constructor uses the continue position only in mode: "continue"; NEW GAME and dev scenes start exactly at state.position.
  • Roamers don't move on CONTINUE (they move on map changes), but wilted Wanderers are checked for recovery on that first load.

A new game

newGameState(ctx) builds the starting state: position and script from WORLD.newGame, 3000 money, the player's home as the first heal point (if it has a healPoint), fresh Wanderers, and options loaded from OPTIONS_KEY. It is also the fallback that normalizeState borrows defaults from.

How to add a field safely

flowchart TD
  A["need to remember something new"] --> Q1{"is it one yes/no fact about the story?"}
  Q1 -->|"yes"| FLAG["use a flag: no save change at all"]
  Q1 -->|"no"| T["add it to GameState in contracts/runtime.ts, optional or with a doc comment on its default"]
  T --> N["newGameState(): give it its starting value"]
  N --> NZ["normalizeState(): read it defensively, default when missing or malformed"]
  NZ --> BIG{"nested object or list?"}
  BIG -->|"yes"| CL["write a cleanX() that keeps only well-formed parts"]
  BIG -->|"no"| RD
  CL --> RD["read sites: tolerate the default too"]
  RD --> TS["save.test.ts: load a literal old envelope without the field, and a junk value"]
  TS --> E2E["npm test, then CONTINUE an old save in the browser"]
  1. Prefer a flag. Most story memory is a flag in state.flags, which needs no save change.
  2. Add the field to GameState in contracts/runtime.ts. Make it optional (?) unless every save will have it after normalisation, and say in the comment what an older save means.
  3. Start it in newGameState().
  4. Repair it in normalizeState(): check the type, clamp numbers, drop unknown ids. Never trust that the stored value has the shape you wrote.
  5. Test the old shape in save.test.ts: build an envelope with the field deleted, and one with a junk value, and check both load. The existing playerLook and nursery tests are good templates.
  6. Leave SAVE_VERSION alone unless you are renaming or restructuring existing data. Then bump it and convert in migrate().
