Battles

Battles are split into two layers that never mix. src/battle/logic/ is pure TypeScript: no canvas, no audio, no timers. Given a battle state, two chosen actions and a random-number function, resolveTurn mutates the state and returns an event log, a list of things that happened ("text", "hp went from 31 to 12", "wilt"). The scene (scene.ts, with hud.ts, fx.ts, movefx.ts and anims.ts) shows the menus and plays that log back as text, animations and HP bars.

The split exists so the rules can be tested and simulated at full speed. Thousands of AI-against-AI battles run in the test suite in seconds (balance tests), and a seeded RNG makes every one reproducible.

State vs. scene

The logic layer's whole world is one BattleState:

export interface BattleState {
  data: GameData;
  sides: [SideState, SideState];
  weather: { kind: Weather; turns: number } | null;
  time?: TimeOfDay;
  wild: boolean;
  /** Display name of the foe trainer, e.g. "WARDEN HOLLIS" (trainer battles). */
  foeTrainer?: string;
  /** Items the foe trainer still has. */
  foeItems: Record<string, number>;
  turn: number;
  /** Dormant counters by Quickened uid. */
  dormant: Record<string, number>;
  /** Player uids that faced the current foe (exp participants). */
  participants: Set<string>;
}

Each side holds its party, the index of the active plant, and volatile state, which lasts only while that plant stays in: stat stages, Root Tap, protecting, the protect chain and flinch. Switching out wipes it (newVolatile()). Side 0 is always the player, side 1 the foe.

Advanced: why an event log, and what it costs
  • The state runs ahead of the screen. resolveTurn finishes the whole turn synchronously, so by playback time a plant may already be at 0 HP. The HUD therefore keeps its own "shown" values (HudView.hp, .level, .status) and animates them from the hp events' from/to. On switch_out, active already points at the newcomer, so the scene reads the outgoing plant from HudView.q.
  • Anything time-sensitive is captured before playback. For wanderers (roaming legendaries) the scene records wandererWiltedAt = new Date() right after resolution, because playback and EXP can run past midnight and the wanderer's recovery is per calendar day.
  • Determinism. All randomness goes through the injected Rng (rng.ts: randInt, chance, pct, seeded mulberry32, sequence for scripted tests). Cosmetic randomness in fx.ts uses Math.random() on purpose, so particles never shift the battle stream.
  • Crash policy. A crash is never a win. The scene snapshots the game state (structuredClone) before main() starts; if main() throws, it logs [battle] crashed, closes any screen it had opened over itself, puts the state back in place (restoreState: party, bag, money, Herbarium and flags as they were; only the play clock keeps running) and finishes with "error". An unknown trainer or a wild request without a species also ends as "error". The overworld then says "Something wilted… The battle is off.", no beat_<id> flag or mark is set, and a script that started the battle stops there (battles in scripts), so the player can fight it again. A trainer whose battle crashed stops spotting the player until the map is reloaded (talking to them still starts the fight), so a repeatable crash can't trap the player in a loop. The e2e playthrough reports every "error" as an issue.
  • Defensive lookups. getSpecies, getMove and getItem in lookup.ts return a plain fallback and warn once for unknown ids, a leftover from when data and battle were built in parallel. The data tests make that path unreachable in practice.

A battle from start to finish

Code asks for a battle with a BattleRequest (wild species and level, or a trainer id, plus canLose, an optional wanderer and a backdrop) and gets back a BattleOutcome: "won", "lost", "fled" or "caught" (or "error" if the battle crashed; see the crash policy above). The scene's main() is one async loop:

    while (!outcome) {
      const choice = await this.chooseAction();
      if (choice.kind === "fled") { outcome = "fled"; break; }
      if (choice.kind === "caught") { outcome = "caught"; break; }
      const pAction: Action = choice.kind === "move" ? { kind: "move", slot: choice.slot }
        : choice.kind === "switch" ? { kind: "switch", index: choice.index } : { kind: "none" };
      const fAction = chooseFoeAction(this.s, this.aiKind, ctx.rng);
      const events = resolveTurn(this.s, pAction, fAction, ctx.rng);
      // …
      await this.play(events);
      outcome = await this.afterTurn();
    }

afterTurn handles the foe's wilt first (EXP is awarded at once, as in Crystal), then your wilt, then the wanderer's flee check, then replacements. Before a trainer's next plant comes out you may switch ("SHIFT" mode): "BRAM is about to use…".

The turn pipeline

resolveTurn runs three phases. Switches and foe items go first, then the two moves in priority and speed order, then end-of-turn residuals.

sequenceDiagram

  participant M as executeMove
  participant E as endOfTurn
  S->>R: player action, foe action
  R->>R: turn++

  R->>R: doSwitch / foeUseItem

  R->>M: second mover (first = false, so no flinch)
  M-->>R: events
  Note over R: 3. residuals in mover order
  R->>E: blight/scorch, Root Tap, weather countdown, frost chip
  E-->>R: events, protect and flinch cleared
  R-->>S: BattleEvent[]
  S->>S: afterTurn: wilt to EXP, switch, outcome
  // 2. Moves by priority, then speed, random tiebreak.
  const movers: Side[] = ([0, 1] as Side[]).filter((sd) => actions[sd].kind === "move");
  // …
  movers.sort((a, b) => {
    const pd = prio(b) - prio(a);
    if (pd !== 0) return pd;
    const sd = effectiveSpeed(s, b) - effectiveSpeed(s, a);
    if (sd !== 0) return sd;
    return 0;
  });
  if (movers.length === 2 && prio(movers[0]) === prio(movers[1]) &&
      effectiveSpeed(s, movers[0]) === effectiveSpeed(s, movers[1]) && rng() < 0.5) {
    movers.reverse();
  }

Effective speed is the Speed stat times its stage multiplier, halved if ROOTBOUND, floored. Stage multipliers follow Gen 2: +n gives (2 + n) / 2, −n gives 2 / (2 + n), clamped to ±6 (so +6 is 4×, −6 is ¼×). Accuracy and evasion use thirds instead: (3 + n) / 3 and 3 / (3 + n).

Advanced: turn-order details and asymmetries
  • Player items never reach resolveTurn. The scene applies a medicine from the bag itself (applyItem), then sends { kind: "none" }. A failed pod and a failed run do the same. Only the foe's item goes through the "item" action (foeUseItem), so the foe's use is part of the event log and the player's is not.
  • A wilted target ends the turn for the other mover. The move loop skips a mover when either the user or the target has 0 HP, so a slower plant whose foe was knocked out doesn't use even a self-targeting move.
  • Flinch needs moving first. executeMove gets first = !acted.has(other); the flinch effect only applies when the target hasn't acted yet this turn and damage was dealt.
  • Priority is read from the chosen slot; Struggle (slot −1) is priority 0. The protect moves (Curl Up, Lotus Effect) are +4, Quick Snap and Vacuum Trap +1.
  • EXP participants are a Set of uids. Every player switch-in adds to it; a new foe (switch or send-out) resets it to whoever is facing that foe. That is how "everyone who faced it" is tracked without a per-turn history.
  • End-of-turn order is the mover order, then any side that didn't move. In a double wilt from residuals, the faster side's residual resolves first.

Executing one move

executeMove is the heart of the battle: it checks whether the user can act, spends PP, rolls accuracy, deals damage and applies effects, in Gen 2 order.

Accuracy combines the move's accuracy with the stage difference: accuracy × accStageMult(clamp(userAccuracy − targetEvasion)). A move with accuracy: null or an always_hit effect skips the roll. Moves that target only the user (most status moves) skip it too, and so does protect.

The damage formula

damage.ts follows Gen 2's order of operations, flooring after each step:

/**
 * Gen 2 order of operations:
 *   base = floor(floor(floor(2L/5 + 2) * P * A / D) / 50)
 *   x2 crit, +2, weather, photoperiod, STAB 1.5, type, random 85..100%.
 * A crit ignores the attacker's negative stages and the defender's positive ones.
 * Scorch halves physical attack.
 */
export function calcDamage(inp: DamageInput): DamageResult {
  // …
  let A = Math.floor(attacker.stats[ak] * statStageMult(aStage));
  const D = Math.max(1, Math.floor(defender.stats[dk] * statStageMult(dStage)));
  if (move.category === "physical" && attacker.status === "scorch") A = Math.floor(A / 2);
  A = Math.max(1, A);

  let dmg = Math.floor(Math.floor(Math.floor((2 * attacker.level) / 5 + 2) * move.power * A / D) / 50);
  if (inp.crit) dmg *= 2;
  dmg += 2;
  if (!inp.typeless) dmg = Math.floor(dmg * weatherMult(inp.weather, move.type));
  dmg = Math.floor(dmg * photoperiodMult(aSpecies.activity, inp.time));
  if (stab) dmg = Math.floor(dmg * 1.5);
  dmg = Math.floor(dmg * effectiveness);
  dmg = Math.floor((dmg * Math.max(85, Math.min(100, inp.roll))) / 100);
  return { damage: Math.max(1, dmg), effectiveness, stab };
}

StatsA / DPhysical: atk vs def. Special: spa vs spd. Stages applied; SCORCH halves physical A.
Critical hit×217/256 normally; 1/8 for high_crit moves (Gen 2 stage table 17/256, 1/8, 1/4, 85/256, 1/2).
Weather×1.5 / ×0.5Sun: fire ×1.5, water ×0.5. Rain: water ×1.5, fire ×0.5. Frost: frost ×1.5.
Photoperiod×1.1A day species attacking by morning or day, or a night species at night.
STAB×1.5Same-type attack bonus: the move's type is one of the attacker's types.

Worked example. A level-10 plant with 20 Attack uses Vine Lash (power 40, wood, STAB) on a water plant with 18 Defence. floor(2·10/5 + 2) = 6; floor(6 · 40 · 20 / 18) = 266; floor(266 / 50) = 5; +2 = 7; STAB floor(10.5) = 10; super effective ×2 = 20; roll 85–100% gives 17 to 20. A critical hit doubles the 5 before the +2: 12 → 18 → 36 → 30 to 36.

The type chart

Nine types, with plant logic first and Gen 2 feel second: wood drinks water, fire burns wood, bug plants eat the pollinators flowers depend on. The design notes for every entry are the comment at the top of typeChart.ts. There are no immunities ("every plant is made of living cells"), so the lowest single-type multiplier is 0.5 and a dual type ranges from 0.25 to 4.

Advanced: numeric edge cases in damage
  • Floors compound. Because every step floors, multiplier order changes results at low damage. STAB-then-type (Gen 2's order) can differ by a point from type-then-STAB. Don't "simplify" the chain into one product: the damage tests pin exact values.
  • Minimum 1. Any hit that lands does at least 1 damage, even 0.25× at level 2.
  • Crits and stages. A crit ignores the attacker's negative stages and the defender's positive ones, but keeps the attacker's boosts and the defender's drops. It doesn't remove SCORCH's halving.
  • Struggle (used when every move is out of PP) is "typeless": no STAB, no chart and no weather, but the photoperiod bonus still applies, and 1/4 recoil. Its type field is "wood" only to satisfy the Move shape, and code identifies it by id.
  • Fixed damage (Wither = the user's level, Fossil Print = 40) bypasses the formula, the chart and crits entirely.
  • Three copies of the effectiveness loop exist: typeEffectiveness in damage.ts, a private effectivenessOf in battle.ts and typeMultiplier in hints.ts. They agree today. If you ever add immunities (a 0 entry), change all three, and note that the eff === 0 "It doesn't affect…" branches are currently unreachable.
  • The AI's expectedDamage calls the same calcDamage with roll: 92 and no crit, so the AI's estimate is always the true midpoint.

Advanced: DORMANT counting and other status subtleties
  • DORMANT skips 0–2 turns, not 1–3. inflictStatus sets s.dormant[uid] = randInt(1, 3). On each attempt to act, canAct subtracts 1; when it reaches 0 the plant wakes and acts that same turn. A counter of 1 therefore costs no turns at all. The test "dormant lasts 1-3 turns" asserts exactly this (skipped === turns - 1), so it's intended. The comment in ids.ts ("can't act for 1-3 turns") reads as if it were stricter.
  • The counter lives on the battle, the status on the plant. A plant still DORMANT when a battle ends keeps the status; in the next battle there is no counter, so canAct rolls a fresh 1–3 and subtracts 1 straight away.
  • Sun prevents frostbite but doesn't cure it. statusImmune checks the weather only when a status is being inflicted.
  • Secondary vs. primary. On a damaging move a status effect is a secondary roll (chance) and is skipped if the target wilted. On a status move it's the main effect: failures are announced ("is already blighted!", "It doesn't affect…"), and a chance below 100 can fail with "But it failed!".
  • Frost weather chips 1/16 max HP from every non-frost plant at the end of each turn while it continues, but not on the turn it ends.
  • Status raises the catch value: +10 for DORMANT and FROSTBITE, +5 for the others (catching).

Advanced: effect interactions
  • Weather counts the turn it's set. turns: 5 is decremented at the end of the same turn, so the weather is active for that turn and four more; "The sunlight faded." prints at the fifth end of turn.
  • Drain and recoil come before the target's wilt, as in Gen 2, so a KO still heals the user. Both need dealt > 0 and a living user.
  • Protect chain. protectChain rises on each success and resets on a failure, on any non-protect move, or when the user can't act. With +4 priority, protect nearly always goes first.
  • Root Tap is volatile: switching the tapped plant out clears it. If the drainer has wilted, the target still loses HP but nobody heals.
  • Status moves that change nothing print "But it failed!" via the anyEffect flag, so a new effect kind must set anyEffect = true when it does something, or every use will also print a failure.
  • Adding a new effect kind touches four places: the MoveEffect union (a contract change), the EFFECTS list in moves.ts, the switch in executeMove, and scoreMove in ai.ts (or the smart AI will value it at 0).

Foe AI

ai.ts has three levels. Wild plants always use "wild"; trainers declare ai: "basic" | "smart" in their TrainerDef (the default is basic, used by route trainers and Rootstock grunts; leaders, the rival and admins such as SHEARS are smart).

scoreMove adds up: expected damage as a share of the target's HP (×100), +40 × accuracy for a likely KO and +15 more if it also has priority; status values (DORMANT 60, FROSTBITE 55, ROOTBOUND 45, BLIGHT 40, SCORCH 35, +15 for SCORCH against a physical attacker); stat changes 28 while there's room (stage below ±2), else 3, and less for self-boosts when below half HP; heals when more than half HP is missing; drain +12 below 60% HP; recoil −8; weather +30 if it boosts one of its own moves, else 4; Root Tap +35 on a non-wood target; protect +8 unless it just protected.

Advanced: what the AI knows and how it is used
  • Full information. The AI reads the real state: your exact HP, status and stages. It doesn't model hidden information, which is the usual trade-off for a small, predictable AI.
  • matchupScore is best outgoing type multiplier − worst incoming multiplier + HP fraction. Switching is only considered when the best move is weak, which keeps smart trainers from switching every turn.
  • The same chooseFoeAction drives the player side in the simulator by swapping the two sides (mirrored in simulate.test.ts). That's why it only ever reads active(s, 1) as "me".
  • A switch is chosen but performed by resolveTurn phase 1, so a switching foe takes your move on its new plant.
  • The items a smart trainer can use are a per-battle copy of TrainerDef.items (foeItems). Rematches clone that list (cloneRematch), so the first fight never drains the second.

Catching with pods

A pod is this game's Poké Ball: a Terrarium Pod (×1) or a Glass Pod (×1.5). In wild battles you can throw one at any time (an updated mechanic). Trainers block it ("Don't be a thief!"), and the pod isn't used up. capture.ts uses the Gen 2 catch value a:

export function catchValue(target: Quickened, catchRate: number, podMultiplier: number): number {
  const M = Math.max(1, target.stats.hp);
  const H = Math.max(0, Math.min(M, target.hp));
  let a = Math.floor(((3 * M - 2 * H) * catchRate * podMultiplier) / (3 * M));
  if (target.status === "dormant" || target.status === "frostbite") a += 10;
  else if (target.status) a += 5;
  return Math.max(1, Math.min(255, a));
}

/** Probability that a single wobble check passes: (a/255)^(1/4). */
export function shakeProbability(a: number): number {
  return Math.pow(Math.max(1, Math.min(255, a)) / 255, 0.25);
}

Four wobble checks must pass, so the overall chance is ((a/255)1/4)4 = a / 255, and a ≥ 255 always holds. The number of wobbles shown is how many checks passed (0–3).

A critical capture is rolled first. Its chance is (a/255) × multiplier / 6, where the multiplier grows with the number of species you've caught: 0 below 1, 0.5 from 1, 1 from 5, 1.5 from 10, 2 from 20, 2.5 from 30. A critical capture does a single wobble check, so it succeeds with (a/255)1/4, far better than a/255.

Worked example. A catch rate 45 plant with 40 max HP. At full HP with a Terrarium Pod, a = floor(40 · 45 / 120) = 15, so 15/255 ≈ 5.9%. At 1 HP, a = 44 (17.3%). At 1 HP and DORMANT with a Glass Pod, a = 66 + 10 = 76: a normal catch is 29.8%. With 12 species caught, the critical chance is 76/255 × 1.5 / 6 ≈ 7.5%, and a critical capture holds 73.9% of the time, so the overall chance is about 33%.

Running away

Gen 2's escape rule: always escape if your speed is at least the foe's; otherwise F = floor(yourSpeed × 32 / (floor(foeSpeed / 4) mod 256)) + 30 × previous failed attempts, and you escape if F > 255 or a 0–255 roll is below F. Running uses raw Speed stats, without stages. You can never run from a trainer.

Advanced: capture edge cases
  • The critical capture counter is herbarium.caught.length, which counts species, not plants, so catching duplicates doesn't raise it.
  • A caught plant keeps its current HP and status, gets metAt, and has its friendship raised to at least 70.
  • catchProbability(a) (used by the catch-curve chart above) returns a / 255 up to floating point and ignores critical captures, so in-game odds are a little higher once you've caught a few species.
  • Wanderers (roaming legendaries) are level 60 with trainer DVs and keep their HP and status between meetings. They flee after the first complete turn, so the realistic plan is a status move or a pod on turn one.
  • When your plant wilts in a wild battle, "Use next QUICKENED?" answered NO tries to run with the first healthy plant's Speed, and failed tries count toward the +30 bonus.

EXP: yield and the share rule

When a foe wilts, the scene awards EXP at once:

/** Gen 2 yield: floor(baseExp * level / 7), x1.5 against trainers. */
export function expYield(data: GameData, defeated: Quickened, trainer: boolean): number {
  const sp = getSpecies(data, defeated.species);
  let e = Math.floor((sp.baseExp * defeated.level) / 7);
  if (trainer) e = Math.floor(e * 1.5);
  return Math.max(1, e);
}

/**
 * Every healthy participant gets the full yield. Healthy party members that
 * sat out get 50%. Wilted members and level-100s get nothing.
 */
export function distributeExp(party: Quickened[], participants: Set<string>, base: number): ExpShare[] {
  const out: ExpShare[] = [];
  party.forEach((q, index) => {
    if (q.hp <= 0 || q.seed || q.level >= MAX_LEVEL) return;
    const participant = participants.has(q.uid);
    const amount = participant ? base : Math.max(1, Math.floor(base / 2));
    out.push({ index, amount, participant });
  });
  // Participants first, in party order (as Crystal announces them).
  return out.sort((a, b) => Number(b.participant) - Number(a.participant) || a.index - b.index);
}

This is an updated mechanic: in Crystal only participants gained EXP (unless one held an EXP Share). Here the whole team grows, but the plants that fought grow twice as fast. Example: a wild Oak Acorn (base EXP 64) at level 5 yields floor(320 / 7) = 45 to each participant and 22 to everyone else; from a trainer it's 67 and 33.

Level-up, move learning and growth after battle

gainExp adds EXP (capped at the level-100 total) and levels up as many times as needed. For each new level it recomputes stats, adds friendship (+5 below 100, +3 below 200, +2 above), and reports the moves learned at exactly that level. It does not teach them: the scene runs the learn flow for each.

Advanced: friendship and growth bookkeeping
  • Friendship −1 on your own wilt is applied in the scene's wiltAnim, not in the logic layer. Simulations (simulate.ts, balance tests) therefore never lower friendship, and moving that line into an animation-skipping path would silently drop it.
  • Growth waits for the end of the battle, as in Crystal, so a plant that passes its growth level mid-battle fights on as its old form. Only the leveled set is checked; see growth triggers.
  • A full move list returns "full" from tryLearn; the flow then offers to forget a move and loops "Stop learning…?" until you decide. "known" moves are skipped silently.
  • A level-100 plant gets no EXP share and so no EVs from that defeat.

Every trainer is a TrainerDef in src/world/trainers.ts (the world section covers placement):

  • Building the team. createTrainerQuickened creates each member at its level with the fixed trainer DVs 9/8/8/8, no sport, and the listed moves if given (else the level-appropriate set). Balance tests and the simulator

Because the logic layer is pure, the test suite can play real battles with the real data. Two files matter most (the testing section covers them in depth):

  • simulate.test.ts is a soak test: 300 seeded battles between random parties of every species at levels 3–42, wild and trainer (some members grafted), with the smart AI playing your side and the basic or smart AI the foe's. After every turn it checks invariants: HP within 0..max and finite, PP never negative, stages within ±6, and every battle ends within 200 turns.
  • balance.test.ts builds a party typical of each story milestone (the starter at an expected level, plus catches available by then) and plays 200–300 seeded fights against each leader and rival, with a greedy "human-like" player that picks the best expected-damage move and never uses items or switches on purpose. Every starter must win more than 25% of the time, and leaders have bands: Flora (the early spike) must average below 75%, Morrow above Flora's average and below 88%, Saguaro 72–90%, Reyes 65–75% and below Saguaro.

simulate.ts (simulateTrainerRun) chains fights the way runtime does, keeping HP, status and PP between rooms and healing only between fights. The Council-run tests use it to check the whole gauntlet.

Advanced: reading and tuning the balance tests
  • The tests log each win rate (console.log), so a near-miss is visible before it fails. Run npx vitest run src/battle/logic/balance.test.ts to see them.
  • The sim player is deliberately pessimistic (no items, no deliberate switches), so a 25% floor corresponds to a comfortably winnable fight for a human. The bands guard shape (Morrow easier than Flora, Reyes harder than Saguaro) as much as absolute difficulty.
  • Results are deterministic (seeded(99)), so a change in any random call order (a new roll in createQuickened, a new AI chance) moves every win rate a little. If a band fails by a hair after a refactor that shouldn't change balance, check for a new RNG draw first.
  • Balance fixtures build the foe with calcTrainerStats and the team's explicit moves, matching runtime, but pass foeItems: {} so single-fight bands don't depend on item luck.
