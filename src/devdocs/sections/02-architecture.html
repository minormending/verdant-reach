Architecture

The runtime has three moving parts. A GameContext (ctx) holds every service and the game state, and is passed to everything. A scene stack holds what is on screen: the overworld at the bottom, a text box or menu on top of it. A fixed-step run loop updates the top scene 60 times a second and draws the stack. This section follows a page load from the first line of src/main.ts to the title screen, then explains each part.

Boot sequence

boot() in src/main.ts is the only code that runs on page load. It builds the pieces in dependency order, starts the loop early so the loading screen can animate, loads the art, and only then pushes the first real scene.

Advanced: why the order matters
  • The error screen goes in first, before anything that can throw, and the whole boot is wrapped in try { … } catch (err) { errors.fatal(err); }. A crash while building the context still shows the "Something wilted…" card rather than a black canvas.
  • The loop starts before loading finishes. The loading scene is a normal scene, so it needs the loop to animate. The onTick callback also feeds ticks, which the error screen uses to tell a dead loop from a live one.
  • booted gates pausing. createPause gets allowed: () => booted && !errors.shown, so a blur during loading never pushes a PAUSED scene on top of the loading scene (whose pop() would then remove the wrong scene).
  • Audio unlock listeners go on pointerup and touchend because touch only grants audio permission on those events (see the unlock rule).
  • Dev handles. In dev builds, window.__vr = { ctx, scenes, pause } exposes the running game to the console and to the e2e driver, and overworld/devDriver installs itself. ?e2e=<suite> loads e2e/playthrough after boot. None of this exists in production.
  • An unknown ?dev only warns and falls through to the title screen, so a typo never leaves you on a blank page.

The GameContext and its services

GameContext is declared in src/contracts/runtime.ts and assembled by createGameContext in src/engine/context.ts. It is the one object that every scene, screen and script receives; nothing reaches another module's internals except through it (or its entry point).

export function createGameContext(deps: { input: Input; scenes: SceneStack; assets: Assets }): GameContext {
  const override = timeOverride();
  const seed = devSeed();
  const battleStreams = new Map<string, () => number>();
  const ctx = {
    ...deps,
    state: undefined as unknown as GameState,
    data: DATA,
    world: WORLD,
    audio: createAudio(),
    rng: seed === null ? Math.random : randomStream(seed, "world"),
    timeOfDay: (): TimeOfDay => override ?? timeOfDayFor(new Date().getHours()),
    battle: (req) => deps.scenes.run((done) => {
      if (seed === null) return createBattleScene(ctx, req, done);
      // …
    }),
  } as GameContext;
  ctx.ui = createUiKit(ctx);
  ctx.screens = createScreens(ctx);
  ctx.save = createSave(() => ctx.state, undefined, () => newGameState(ctx));
  ctx.state = newGameState(ctx);
  return ctx;
}

Notice the two-phase build: the plain services go into the object literal, then ui, screens and save are added afterwards because they need ctx itself. save takes a getter (() => ctx.state) rather than the state object, so it always saves whatever state is current.

Advanced: invariants and traps
  • Never cache ctx.state. NEW GAME (runNewGame) and CONTINUE (the title's continueGame) assign a new object to ctx.state. Hold ctx and read ctx.state when you need it.
  • Battles get a shallow copy under ?seed. The seeded path calls createBattleScene({ ...ctx, rng }, req, done). Mutating state through the copy works (same object); reassigning a field on the copy would not reach the real ctx. Battle code must only mutate.
  • playClock is a module-level flag in engine/context.ts, not a context field. The overworld's enter() sets it, the title clears it, and play time accrues only while it is set and the game isn't paused.
  • Construction order. createScreens applies the saved volumes in a queueMicrotask ("once audio exists"), i.e. after createGameContext has returned. Adding a service that needs ctx.ui or ctx.screens at construction time means placing it after them.
  • Extending the context is a contract change (GameContext lives in src/contracts). Prefer a function in your module that takes ctx; add a field only when many modules need the same service.

Scenes and the scene stack

A scene is anything that updates and draws (runtime.ts):

export interface Scene {
  /** If true, the scene below is drawn first (menus, text boxes over the map). */
  transparent?: boolean;
  enter?(): void;
  exit?(): void;
  update(dt: number): void;
  draw(g: CanvasRenderingContext2D): void;
}

The stack has two rules that explain almost everything about how the game feels:

  1. Only the top scene updates. When a text box is on top of the overworld, the overworld is frozen: no walking, no NPC timers. That is also how pausing works.
  2. Drawing starts at the highest opaque scene. The loop walks down from the top past transparent scenes and draws from there upwards, so a menu appears over the map.

The most important method is run. It pushes a scene and returns a Promise that resolves when the scene calls done(result). This turns "show a text box and wait for A" into an ordinary await, which is why story scripts, menus and battles read like straight-line code (from core.ts): 

    run<T>(factory: (done: (r: T) => void) => Scene) {
      return new Promise<T>((resolve) => {
        let scene: Scene;
        scene = factory((r) => {
          const i = stack.lastIndexOf(scene);
          if (i >= 0) { stack.splice(i, 1); scene.exit?.(); }
          resolve(r);
        });
        api.push(scene);
      });
    },

Advanced: lifecycle edge cases
  • enter() runs only on push. When the battle above the overworld is removed, the overworld is revealed but gets no callback. A scene that must react to regaining the top has to do it in the code that awaited the child (the overworld's battle() restores music and fades in after await ctx.battle(...)).
  • done removes the scene wherever it is, not necessarily from the top (lastIndexOf + splice). The pause overlay relies on the same trick.
  • A run scene removed by someone else never resolves. clearScenes (used by NEW GAME and the end of the story) pops everything; any promise still awaiting a popped run scene stays pending forever. That is intended when abandoning a flow, but never pop() a run scene by hand if someone awaits it.
  • Calling done twice splices nothing the second time (the scene is no longer found) but still calls resolve, which is harmless for promises. Flows such as runFlowScene still guard with a finished flag.
  • Throwing in update or draw escapes the frame callback, so the loop stops scheduling itself and the error card appears (see errors). Async flows should catch: the overworld's flow() is documented "Errors never escape."
  • Async work that waits on frames (Timers.frames, Fader.to) only progresses while the owning scene is on top and ticking them; that is a feature (pause freezes cut-scenes) but means a scene must not await its own timers while a child it pushed is on top.

Module boundaries and contracts

Contracts are the shared language: everything one module needs to know about another's data or services, and nothing else. They live in src/contracts/ and are re-exported from its index.ts, so the usual import is import { … } from "../contracts".

Advanced: where the graph departs from the rule, and how to change it safely
  • Deep imports exist. For example screens imports battle/logic/* (exp, items, lookup, stats), engine/random.ts imports seeded from battle/logic/rng, platform imports drawText/drawWindow from ui/kit, and overworld imports several ui/* files. They are pure helpers, but they are coupling the contracts don't show.
  • Folder-level cycles exist: battle ⇄ screens, overworld ⇄ ui, overworld ⇄ save, world ⇄ overworld and engine ⇄ ui (context imports ui/kit; ui imports engine/gfx). ES modules tolerate cycles of functions, but a cycle that touches a top-level value evaluated at import time (DATA, WORLD, a const table) can hit the temporal dead zone and throw "Cannot access before initialization". Keep top-level work out of modules that sit on a cycle, or break the cycle with a dynamic import() as main.ts, ui/title.ts and ui/newgame.ts do for the overworld.
  • Contracts are frozen by convention. Adding an id to a list in ids.ts is a contract change; adding content under an existing id is not. Keep contract types minimal: a field added to GameState is a save-format change and needs a migration in src/save (old saves must still load; see how playerLook is optional).
  • New cross-module needs: export from the provider's index.ts, not from a deep file, so the provider can refactor freely.

Dev scenes and URL flags

A dev scene lets you start the game straight into one module with fixture data. ?dev=<dir> loads src/<dir>/dev.ts, whose default export is (ctx: GameContext) => Scene | Promise<Scene>. main.ts finds them with import.meta.glob("./*/dev.ts"), so adding a module's dev scene is just creating the file.

Advanced: dev scenes in production, and flag gating
  • ?dev is not gated on import.meta.env.DEV. The glob is lazy, so every dev.ts becomes its own chunk in dist/ and loads only when asked for. That is deliberate for the Art Lab ("Works in dev and in the production build"), but it means fixture code ships. Never put secrets or destructive actions in a dev scene.
  • Gating differs per flag. ?seed, ?speed and ?e2e are dev-only; ?time, ?timer, ?art, ?touch and ?nopause also work on the live site, which is handy for bug reports ("does it happen with ?time=day?").
  • Platform flags (platformFlags) switch off the shell for the ?dev=world overview (a plain document) and switch off pause-on-blur for hidden test panes and e2e runs, which must never pause themselves.
  • Writing a dev scene: build fixtures on a fresh ctx.state, return a scene (or a promise of one), and keep it out of the production flow; src/screens/kit/devhook.ts shows how a dev scene can freeze the loop and step exact frames for screenshots.
