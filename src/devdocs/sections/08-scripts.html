Story scripts

Every cutscene, conversation, shop and gift in Verdant Reach is a script: a plain array of commands (ScriptCmd[]) stored in WORLD.scripts under a script id. Scripts are data, not code. They can't call functions or loop; they say lines, set flags, branch on flags and ask the engine to do things.

Why data? Three reasons. Writers can work on scenes without touching the engine. The validator can read every script and check it (text fit, references, which items a scene gives) without running the game. And the interpreter can run on a fake host in unit tests, so a scene's logic is testable in milliseconds.

ScriptCmd ops

A ScriptCmd is an object with an op field naming what it does, defined as a TypeScript union in contracts/world.ts. There are 56 ops. A few, straight from the contract:

export type ScriptCmd =
  | { op: "say"; text: string; speaker?: string }        // auto-wrapped, paged
  | { op: "choice"; prompt?: string; options: string[]; branches: ScriptCmd[][] }
  | { op: "yesno"; prompt: string; yes: ScriptCmd[]; no: ScriptCmd[] }
  | { op: "if"; when: Cond; then: ScriptCmd[]; else?: ScriptCmd[] }
  | { op: "ifTime"; time: TimeOfDay[]; then: ScriptCmd[]; else?: ScriptCmd[] }
  | { op: "setFlag"; flag: string; value?: boolean }      // default true
  | { op: "giveItem"; item: ItemId; qty?: number }
  // …
  | { op: "battle"; trainer: TrainerId; canLose?: boolean } // sets flag `beat_<trainer>` on win
  | { op: "wildBattle"; species: SpeciesId; level: number; sport?: boolean; canLose?: boolean }
  | { op: "ifLastBattle"; result: Exclude<BattleOutcome, "error">; then: ScriptCmd[]; else?: ScriptCmd[] }
  // …
  | { op: "call"; script: ScriptId }
  // …
  | { op: "end" };

Advanced: optional host methods and op history

Ops were added in rounds (the contract marks "Round 3" and "Round 4" groups). Later presentation ops call optional host methods (host.camera?.(…), host.still?.(…), host.flash?.(…)), so a minimal test host that doesn't implement them simply skips those commands. State-changing ops never go through optional methods: a script's effect on flags, the bag and the party is the same on every host, which is what makes the chapter tests meaningful.

The interpreter

The interpreter is overworld/script.ts. It is small: runScript resolves a script id (or takes an inline list), exec runs commands one after another, and step is one big switch on op. Every command is awaited, so a say waits for the player to press A, a moveNpc waits for the walk to finish, and a battle waits for the whole fight.

export async function runScript(
  host: ScriptHost, script: ScriptId | ScriptCmd[], state: ScriptState = { depth: 0 },
): Promise<void> {
  if (script === WHITEOUT_SCRIPT) {
    await host.whiteout();
    throw new ScriptAbort("whiteout");
  }
  try {
    await exec(host, resolve(host, script), state);
  } catch (e) {
    if (e instanceof ScriptEnd) return;
    throw e;
  }
}

async function exec(host: ScriptHost, cmds: ScriptCmd[] | undefined, st: ScriptState): Promise<void> {
  if (!cmds) return;
  for (const cmd of cmds) await step(host, cmd, st);
}

And a slice of step, showing how branches simply pick which list to exec next:

switch (cmd.op) {
  case "say":
    return ctx.ui.say(cmd.text, cmd.speaker ? { speaker: cmd.speaker } : undefined);
  case "choice": {
    const i = await ctx.ui.choose(cmd.options, { prompt: cmd.prompt, cancel: false });
    return exec(host, cmd.branches[i < 0 ? cmd.options.length - 1 : i], st);
  }
  case "yesno":
    return exec(host, (await ctx.ui.yesNo(cmd.prompt)) ? cmd.yes : cmd.no, st);
  case "if":
    return exec(host, checkCond(cmd.when, flags) ? cmd.then : cmd.else, st);
  case "ifTime":
    return exec(host, timeMatches(cmd.time, mapTime(host.map(), ctx.timeOfDay)) ? cmd.then : cmd.else, st);
  case "setFlag":
    flags[cmd.flag] = cmd.value ?? true;
    return;
  // …
}

The ScriptHost

The interpreter never touches the map, the camera or actors directly. It calls a ScriptHost: an interface with methods like warp, movePlayer, moveNpc, face, fade, battle, whiteout and still. In the game, the overworld builds the host (makeHost() in overworld/index.ts). In tests, script.test.ts passes a fake host made of spies. This is a port: a seam where the real world plugs in.

Advanced: control flow, aborts and errors
  • call is a subroutine that shares the caller's state (ScriptState), so ifLastBattle after a call sees a battle fought inside it. Calls nest at most 16 deep, then throw.
  • end stops the whole run, callers included. It throws ScriptEnd, which only runScript catches; call doesn't. So an end inside a called script also ends the script that called it. Prefer an if around the rest of the script when you mean "return".
  • ScriptAbort is thrown after a whiteout (a lost battle without canLose, or call: "whiteout") and after endSlice. flow() swallows it quietly; any other error is logged with console.error and control still comes back. A broken script never freezes the game.
  • Unknown ops and ids warn, never crash. An unknown script id runs as an empty list; an unknown op logs and is skipped. The validator turns both into test failures, so they never ship.
  • No compile-time exhaustiveness. step ends in a default that warns, so TypeScript won't tell you if you add an op to the union and forget its case. See the checklist below.
  • Re-entrancy. flow() counts, so a script that triggers another flow (a warp with an onEnter) nests correctly; settle() runs only when the count returns to zero. A script warp made while the screen is already black defers the destination's onEnter until the script fades back in.

Flags and conditions

A flag is a named boolean in state.flags, saved with the game. Unset means false. Flags are how the world remembers: got_starter, pip_demo_done, lake_calmed. Names are snake_case. Some are set by the engine, not scripts:

FlagSet when
beat_<trainerId>A trainer battle is won (sight, talk or battle op)
picked_<map>_<npcId>An item ball is picked up
hidden_<map>_<x>_<y>A hidden item is found
pruned_…, bridged_…, filled_…A field tool clears a cell
quest_<id>_started, quest_<id>_donestartQuest, completeQuest
visited_<town>Entering a map that proves a town was reached (SEED GLIDE)
wanderer_caught_<id>A Wanderer is caught

In script files you rarely write the raw objects. The shorthands in build.ts read like prose:

export const say = (text: string, speaker?: string): ScriptCmd =>
  speaker ? { op: "say", text, speaker } : { op: "say", text };
export const flag = (name: string, value = true): ScriptCmd =>
  value ? { op: "setFlag", flag: name } : { op: "setFlag", flag: name, value };
export const ifFlags = (spec: Record<string, boolean>, then: ScriptCmd[], els?: ScriptCmd[]): ScriptCmd =>
  els ? { op: "if", when: when(spec), then, else: els } : { op: "if", when: when(spec), then };
export const ifNight = (then: ScriptCmd[], els: ScriptCmd[]): ScriptCmd =>
  ({ op: "ifTime", time: ["night"], then, else: els });

The most common pattern in the whole game is the once-only scene: check a "done" flag, play the scene, set the flag at the end. It makes onEnter and triggers safe to fire again.

ch9_arrival: [
  ifFlags({ ch8_done: true, ch9_arrived: false }, [
    camera(15, 17, 60),
    say("THISTLEDOWN, on the desert's edge. Tumbleweed country."),
    say("A dry wind blows through the square. It smells of dust and warm stone."),
    flag("ch9_arrived"),
    flag("visited_thistledown"),
    call("ch9_tumbleweed"),
    cameraReset(),
  ]),
],
Advanced: flag hygiene
  • Flags are forever. Nothing deletes a flag; setFlag with value: false stores false. Use that to reset a repeatable sequence, as the Council does with COUNCIL_RUN_FLAGS.
  • Acquisition flags don't give items. Field-tool gates key on flags like got_raft and got_saxifrage, but the validator only counts a giveItem as granting the tool. Always give the item and set the flag together.
  • Positive conditions drive the proof. The progression explorer treats a flag as reachable once some reachable script sets it to true. A condition like { x: false } is assumed satisfiable (flags start false), so an else that only runs after a flag is set is explored only as far as that flag is reachable.
  • Engine-owned names. Don't hand-set beat_*, picked_* or hidden_* flags except to reset them; their meaning is defined by engine code.

say() and the text-box rules

The text box is Crystal's: 18 columns by 2 lines of an 8x8 font (TEXTBOX in constants.ts). ctx.ui.say wraps the text at word boundaries and types it out. When two lines are full it waits for A, then scrolls up one line, as on a Game Boy.

flowchart LR
  T["say(text, speaker)"] --> P["prefix: SPEAKER: text"]
  P --> R["replace tokens: PLAYER and RIVAL names"]
  R --> W["wrap at 18 columns"]
  W --> B["type out 2 lines, wait for A, scroll"]
  T -.->|"at test time"| V["validator: expand tokens to 7 wide letters, wrap, count pages of 2 lines"]
  V --> OK{"3 pages or fewer, no word over 18?"}
  OK -->|"no"| ERR["test failure with the line"]
  • Speaker prefix. say("Gotcha!", "PIP") displays PIP: Gotcha!. The prefix counts toward the length. Narration has no speaker.
  • Tokens. <PLAYER> and <RIVAL> are replaced with the names (the UI also accepts {PLAYER} and [PLAYER], but world data uses the angle form, which is what the validator measures). Names are at most 7 letters, so the validator measures each token as WWWWWWW.
  • At most 3 pages. A page is 2 wrapped lines, so one say holds at most 6 lines. Longer thoughts are several says: one idea per box (STYLE.md §5).
  • Upper-case names in dialogue: DR. VALE, BRAM, the HERBARIUM.
  • The player is a boy or a girl (state.playerLook), so keep lines about the player neutral.

The validator's check, from validate.ts:

case "say": {
  for (const line of wrapText(expandTokens(c.text))) {
    if (line.length > TEXTBOX.cols) errs.push(`${at} word too long: "${line}"`);
  }
  const shown = (c.speaker ? `${c.speaker}: ` : "") + expandTokens(c.text);
  const pages = Math.ceil(wrapText(shown).length / TEXTBOX.lines);
  if (pages > 3) errs.push(`${at} ${pages} pages: "${c.text}"`);
  break;
}
The error message quotes the whole line. Fix it by splitting into two says at a natural beat, not by squeezing words: the box reads best with short sentences.
Advanced: two wrappers, and what they disagree on

The validator has its own wrapText rather than importing the UI's (ui/font.ts), so world tests don't load DOM code. They agree on normal text. They differ on a single word longer than 18 characters: the UI hard-breaks it, the validator reports it. They also differ on page breaks: the UI treats a form feed or a blank line as a new page, while the validator only counts lines. Avoid both in world text and the two stay in step.

Trainer intro, defeat and after lines go through the same word check but not the 3-page check, so keep them short by hand.

Branches: calls, ifLastBattle and ifTime

Every branching op has a then list and an optional else. They differ only in the question asked:

OpAsks
ifDoes the Cond hold (all flags as given)?
ifTimeIs the map's time of day one of these? (A map's forced time beats the clock.)
ifLastBattleDid the last battle in this run end won, lost, fled or caught?
ifHasItemIs at least qty (default 1) in the bag?
ifPartyHas, ifCaughtIs any of these species in the party, or ever caught?
ifCaughtCountHave at least N species been caught?
ifMarksHave all of these marks been earned?
ifNurserySeedIs a seed waiting at the Nursery?

call runs another script by id, then carries on. Chapter files use it to share pieces: ch9_arrival calls ch9_tumbleweed, and the same script is also the talk script of the tumbleweed NPC in the square, so whichever happens first plays it (its own tumbleweed_seen check stops it playing twice). A special id, "whiteout", runs the whiteout recovery and aborts.

Without canLose, losing sends the player to the last heal point and nothing after the battle runs. Put the flag that marks a scene done after the battle, so a loss lets the player try again. The Council seats in ch11.ts go further: the win is recorded by an ifLastBattle: "won" branch that calls the seat's _after script.
Advanced: marks, outcomes and sight battles
  • Marks are awarded once, by one owner. After a won leader battle, trainerBattle gives the trainer's mark only if no script anywhere contains a giveMark for it (scriptsAwardMark scans all scripts on each win). So if a leader's scene gives the mark itself, the engine stays out of the way.
  • ifLastBattle only sees battles in this run. A trainer who spots you from the grass fights outside any script, so there is no "last battle" for a later script to read; use the beat_<trainer> flag instead.
  • A crashed battle ("error") stops the script with ScriptAbort before lastBattle is set, so neither branch of an ifLastBattle runs (a canLose rival scene doesn't carry on as a loss either) and the callers of a called battle script stop too. The battle scene has already put the state back as it was, so the scene can simply be started again. This relies on scenes setting their "done" flag after the battle, which every scene does today; ifLastBattle can't name "error" (the type excludes it).
  • fled and caught only come from wild battles. A wildBattle with canLose needs branches for every outcome that matters, or the scene continues as if nothing happened.
  • After every battle the overworld sets 3 grace steps, restores the map music and fades back in, except after a non-canLose loss, where whiteout fades in instead.

Advanced: the checks behind gifts and trades
  • The validator rejects unknown items, species, marks, shop stock and trade species, a trade level outside 1 to 60, and a trade nickname over 10 characters.
  • Every harvest must name a bush that exists as an NPC bush:<id>, and every bush's script must harvest its own id. Bush ids must be unique across the whole world, because the picked date is stored per id.
  • Harvest days use the player's local date, so changing the device clock changes when bushes refill. That is accepted, as in Crystal's real-time clock.
  • giveSpecies records metAt (map and level) and adds to both seen and caught, so a gift counts toward Herbarium totals and ifCaughtCount.

Stills, credits and the Hall of Fame

A still is a full-screen 160x144 story illustration. still fades the map out and the picture in; text boxes draw over it; stillClear fades back. Keep them rare (one to three boxes each). If a script forgets stillClear, settle() clears it when the scene ends. If the art is missing, the still is skipped with one warning, so scripts still read.

The ending in ch11.ts strings the end-game ops together:

{ op: "stillClear" }, { op: "hallOfFame" }, { op: "credits" },
flag("game_cleared"), flag("council_run", false),

hallOfFame appends a snapshot of the party (species, level, nickname) to state.hallOfFame, one entry per clear. credits rolls the cast from credits.ts; B skips, and the script then continues. endSlice (the old vertical-slice ending) offers a save, shows "to be continued" and returns to the title.

Quests

Side quests live in quests.ts. A QuestDef is display data for the NOTES screen: a title (16 characters at most), giver, area, ordered steps and a reward line. Each step is ticked when its doneWhen condition holds, so a step can be any flag, including a hidden-item flag.

lost_climber: {
  id: "lost_climber", title: "LOST CLIMBER", giver: "MOUNTAINEER, ROUTE 9", area: "route_9",
  steps: [
    { text: "Find the lost CLIMBER PACK.", doneWhen: [{ flag: "hidden_route_9_8_8", is: true }] },
    { text: "Return it to the MOUNTAINEER.", doneWhen: isDone("lost_climber") },
  ],
  reward: "2 RAIN JARS + COLD SNAP",
},
stateDiagram-v2
  [*] --> None
  None --> Started: startQuest, toast NEW NOTE
  Started --> Started: giver reminds
  Started --> Done: completeQuest, toast and quest jingle
  None --> Done: completeQuest (goal already met)
  Done --> Done: after-line, no reward again

Every giver handles four states (not started, started, goal met, done). The file's helper byQuest branches on them in the right order: done first, then started, then fresh. After completeQuest a giver always says one more line, so the jingle never ends a script with no box open.

Advanced: quest invariants
  • startQuest is a no-op once a quest is started or done, so a giver can call it every time without stacking toasts. completeQuest sets both flags, which lets a quest be finished in one visit.
  • QUEST_GIVERS in validate.ts pins the early quests' giver NPC ids, maps and script ids, and quest NPCs are checked never to block a path (mustNotBlock).
  • Quest scripts deliberately never face, emote or move the quest NPC by id; talking already turns an NPC to the player, and this keeps the scripts valid wherever the NPC is placed.
  • A doneWhen can point at any flag the engine sets, such as hidden_route_9_8_8. If you move that hidden item, the quest step breaks silently: grep for the old flag.

A chapter file opens with a comment naming its design doc and the voice rules, defines a few local helpers (call, camera, byStarter for lines that depend on the starter), then the scripts, roughly in story order. Chapters 4 to 11 and the post-game have a matching *.test.ts beside them that checks their flags and scenes.

Advanced: keeping chapters independent
  • Merge order doesn't matter (ids are unique), so a chapter can be added or split without touching the others beyond world/index.ts.
  • Script ops address NPCs by id on whatever map is current when the op runs. A script called from two maps must only name NPCs both maps have, or guard with if.
  • Keep chapter helpers (byStarter, camera, call) local to the file. Shared helpers belong in build.ts only when three or more chapters need them.
  • A chapter test drives the real WORLD scripts through the interpreter with a fake host and checks the flags after each scene, which catches ordering mistakes the static validator can't.

Worked example: PIP's catching demo

Let's trace one real scene from the first flag to the last. It spans three files: story.ts, route_1.ts, and the Bramblegate and Sugarbush maps.

1. The flag that arms it. In his Hedgerow house, talking to FENNIMORE runs fennimore, which gives the Centuryheart seed and ends with flag("got_seed").

2. The trigger and the NPC wait for it. On Route 1 the lane is two tiles wide at row 2. A trigger covers both tiles, and PIP stands nearby, both gated on the same condition:

{ id: "pip", sprite: "pip", x: 12, y: 3, facing: "left", movement: "static", script: "pip_demo",
  visibleWhen: when({ got_seed: true, pip_demo_done: false }) },
// …
triggers: [
  { x: 9, y: 2, w: 2, script: "pip_demo", when: when({ got_seed: true, pip_demo_done: false }) },
],

Before FENNIMORE, PIP is invisible (and not solid) and the trigger is inert. Afterwards, the Hedgerow exit lands the player on (9,1) or (10,1) facing south, so the very first step onto Route 1 lands on (9,2) or (10,2), and onArrive finds the trigger. PIP also has script: "pip_demo", so walking up and talking to him plays the same scene.

3. The scene runs. Shortened from story.ts:

pip_demo: [
  emote("pip", "!"),
  face("pip", "toPlayer"),
  say("You're DR. VALE's new botanist! I'm PIP! I know facts!", PIP),
  moveNpc("pip", "left"),
  say("Have you caught one yet? No? Watch! Watch watch watch!", PIP),
  // … pod throw: sfx and waits …
  { op: "jingle", id: "caught" },
  emote("pip", "♪"),
  say("Gotcha! A LION'S TOOTH! That's a baby DANDELION!", PIP),
  // … three tips and a true fact …
  say("DR. VALE has pods at the HERBARIUM. Ask her! Bye, <PLAYER>!", PIP),
  moveNpc("pip", "left", ...steps("down", 5)),
  { op: "hideNpc", npc: "pip" },
  flag("pip_demo_done"),
],

4. The flag closes it and opens what comes next. hideNpc hides PIP right now; pip_demo_done keeps him hidden forever (his visibleWhen fails) and switches the trigger off. The same flag is the visibleWhen for PIP's later appearances in Bramblegate and Sugarbush.

The flag is set on the last line. If the player could be interrupted mid-scene (a battle they could lose), setting it last means the scene replays rather than being lost.
Advanced: how the validator sees this scene

The progression explorer reads fennimore statically and records "sets got_seed". When it later floods Route 1, it sees the trigger and PIP are available once got_seed is true, scans pip_demo, and records "sets pip_demo_done, needs got_seed". At the fixed point both flags are known reachable, so the Bramblegate PIP counts as reachable too. The text check runs over every say: "PIP: " plus the line must fit 6 lines, with <PLAYER> measured 7 wide.

Adding a new op safely

  1. Add the variant to ScriptCmd in contracts/world.ts (contracts change deliberately; keep it minimal).
  2. Add its case to step() in script.ts. If it needs the map or actors, add a method to ScriptHost and implement it in makeHost().
  3. If it has nested command lists, add it to childLists() (script.ts), eachCmd() and the commands() switch inside progress() (validate.ts). Otherwise the validator won't see inside it, and the text and reachability checks silently skip those lines.
  4. Add reference checks to checkCmds in validateWorld (unknown ids should fail tests).
  5. Write a test in script.test.ts with the fake host.
