Testing

Verdant Reach has no QA team, so the tests stand in for one. They are organised as a test pyramid: many small, fast tests at the bottom that check one function at a time, a middle layer of checks that sweep the whole game's data (every map, every boss, every art bundle), and at the top a single slow test that plays the entire game from NEW GAME to the post-game in a real browser. A separate gate, release-check, makes sure no placeholder text or art reaches main.

flowchart TB
  E2E["Headless playthrough: 1 run, 217 beats (npm run e2e)"]
  WIDE["Whole-game checks: world validator, environment digests, balance bands, art bundles"]
  UNIT["Unit tests: about 1,670 vitest tests in 139 files, next to the code (npm test)"]
  RC["release-check: no placeholders on main"]
  E2E --- WIDE
  WIDE --- UNIT
  RC -.-|gate in CI| WIDE

Why this shape? A unit test that fails names the broken function in a second. The playthrough takes most of an hour and only tells you where the game got stuck, so it is the last line of defence, not the first. If the playthrough is the only test that catches a bug, a cheaper test is missing.

Unit tests by area

A unit test checks one piece of pure logic (a function with no screen, no clock and no browser) against known inputs. Tests live next to the code they test, as foo.test.ts beside foo.ts. There is no vitest.config.ts at the root, so Vitest reads vite.config.ts and uses its default pattern: any *.test.ts anywhere in the repository (outside node_modules) runs in npm test, including the playthrough's own unit tests in e2e/.

Advanced: running the overworld without a browser

The UI-flow tests and e2e/field-input.test.ts run the real overworld scene, modal screens and script interpreter in Node. They stub only the browser globals the engine touches (location, addEventListener, KeyboardEvent, document.getElementById), use vi.useFakeTimers(), and pass an assets object whose image() returns null. Drawing and audio are skipped; everything else is the shipping code. This is why the engine reads location.search defensively and why scenes must not assume an image has loaded.

Because tests share module-level state (the WORLD object is a singleton), a test must never mutate WORLD directly. Clone it. Tests that reset modules between cases (vi.resetModules()) do so because e2e/playthrough.ts keeps its report and hooks at module level.

Test time is dominated by the balance simulations (thousands of seeded battles) and the validator's floods. The 20-second per-test timeout in npm test exists for them; if a new whole-game test needs more, make it cheaper rather than raising the timeout.

The balance simulator and its bands

Difficulty is tested, not eyeballed. balance.test.ts plays each important battle hundreds of times with a party that a typical player would have at that point in the story, and checks that the win rate falls inside a band: a minimum and maximum agreed in the chapter plan. If someone makes FLORA too easy or MERCER impossible, the test fails before the change ships.

  M["Milestone: trainer id, starter level, extra party members"] --> L{"For each starter: oak, chili, lily"}
  L --> P["Build the party with createQuickened, seeded(99)"]
  P --> F["Build the foe team at its real stats and moves"]
  F --> B["Battle: greedy player vs the trainer's AI, up to 300 turns"]

The simulated player uses a greedy policy: always the move with the best expected damage (power x STAB x type x stat ratio x accuracy). It never heals or switches on purpose, so the rates are pessimistic: a real player does better. If a band fails after your change, do not widen the band to make it pass. Retune the trainer (levels, moves, items) or your change. A band only moves with a decision recorded in the chapter plan, and the commit body must say why.
Advanced: determinism and what shifts the rates

Every rate is computed from seeded(99), so the same code gives the same numbers on every machine; the test logs them (console.log) so you can compare before and after. The flip side: anything that changes the order or number of random draws (a new accuracy roll, an AI that rolls once more per turn, a new secondary effect) shifts every rate a little even if the mechanic is balance-neutral. A rate that moves by a point or two is noise of this kind; a rate that moves by ten is a real change.

The relational checks (ROOK below SIGNE and FLORA, MERCER below the earlier spikes) encode the difficulty curve itself, so you cannot pass by moving every leader together. The single-fight fixtures give neither side items (foeItems: {}), because the sim player cannot use them either; only the Council run allows bag healing between rooms.

The balance file is the slowest part of npm test. When adding a milestone, prefer reusing an existing party core and n = 200 to 300; fewer than about 120 battles gives rates too noisy for a ten-point band.

Environment digest tests

Each late chapter had an environment pass: an art round that replaced the stand-in tiles of finished maps with new scenery (cable runs in the Relay, sandstone in the canyon, frost in the Seed Vault). Such a pass must change how a map looks but never how it plays. The *-environment.test.ts files in src/world/ (Chapters 6 to 11 and the post-game) enforce that.

They work by taking a digest: a projection of each map down to the parts that affect gameplay, turned into a JSON string and hashed with SHA-256. The expected hash was recorded from the stand-in maps before the pass. If any gameplay field changes, the hash changes and the test fails.

  G --> J["JSON.stringify"]
  J --> H["SHA-256"]
  H --> Q{"equals the pinned digest?"}
  Q -- yes --> OK["pass: only looks changed"]
  Q -- no --> FAIL["fail: gameplay changed"]

Some files go further. postgame-environment.test.ts also freezes what every cell does in each flag state. It maps every tile to a role (walkable or solid, slide, encounter, water, ledge, field move, pit, exit mat, lamp, interact), so a cosmetic swap such as wall to vault_wall keeps its role and passes, while a new solid tile in a corridor fails. Others check one puzzle "cell for cell" or prove every trainer still sees down an open lane.

Re-pinning needs a reason. Sometimes a gameplay change is intended (a bug fix moves an NPC). Then you update the digest, and you write a comment above it saying what changed and why, as in the example above. A bare new hash with no comment tells a reviewer nothing and hides accidental changes made in the same commit.

Advanced: debugging a digest failure

A hash says that something changed, not what. To find it, log gameplay(id) on your branch and on the commit before your change (check that commit out in a separate worktree), and diff the two JSON strings.

Watch for a subtle trap: JSON.stringify keeps the order in which properties were written. Rewriting a warp as { to, x, y, toX, toY } instead of { x, y, to, toX, toY } changes the digest although the game behaves the same. Keep the existing property order when you touch frozen maps.

Files that allow an intended cosmetic change exclude it explicitly rather than re-pinning: Chapter 8 filters out the lobby's banner swap (isBannerSwap), and the post-game file hashes METHUSELAH as its potted-plant stand-in (RESKIN). Prefer that pattern when the change really is cosmetic, because it keeps the rest of the digest strict.

The world validator as a test

validate.ts is a static checker for the whole world: it never runs the game, it reads WORLD and returns a list of human-readable error strings. One test in world.test.ts turns it into a gate:

it("passes every structural check", () => {
  expect(validateWorld(WORLD)).toEqual([]);
});

Because the result is a list of strings, a failure prints every problem at once, each prefixed with where it is: [route_4] warp lands on solid glasshouse_city 6,13. The same checker runs in the browser in the world dev scene (?dev=world, src/world/dev.ts), which lists them and tints unreachable tiles red.

Advanced: the validator's movement model

The validator has its own model of movement (grid, walkable, flood, canReach): one-way ledges, ice that slides to a stop, rafting on water, root bridges, boulder pits. It must agree with the overworld's real rules in src/overworld/. When you add a movement mechanic, update both and add a test that compares them; validate.test.ts already checks that the reverse search canReach agrees with forward flood for every start and target on small grids.

canReach is a single reverse flood from the exits, which made the soft-lock check about 35 times faster than flooding from every tile. Any rule that is not symmetric (ledges, ice) must be reversed correctly there.

Warnings (the optional second argument) are for content that is allowed to be unfinished, such as a quest script not wired yet. They never fail the test.

The headless full playthrough

The top of the pyramid is a robot that plays the whole game. npm run e2e builds the game through the production pipeline, serves that build on a private port, opens it in headless Chromium through Playwright, and lets a script in e2e/playthrough.ts press real keys from the title screen through Chapter 11, the credits and the post-game. It records 217 beats: named checkpoints such as "starter: oak" or "HOLLIS: bramble mark", each with the new story flags, the map, the position and a 160x144 screenshot.

Production build, plus test hooks. By default the runner calls Vite's build() with mode: "e2e" and outDir: "dist-e2e" (git-ignored), then serves that folder with preview(). That is the same pipeline as npm run build (bundling, chunk splitting, minification, the relative base), so a bug that only exists in the shipped bundle fails the playthrough. The one difference is the mode: the test hooks are on only when import.meta.env.DEV or import.meta.env.MODE === "e2e" (testHooks.ts): ?speed, ?seed, ?e2e, the scene stack (window.__vr), the battle scene (window.__battle) and the key driver (window.__t, from devDriver.ts). Vite replaces both values at build time, so the public build (mode production) ignores those parameters, and src/main.ts spells the check out inline so that build drops the driver and the playthrough chunk entirely. Beats

The story is written as a chain of guarded steps. Each step is skipped if its flag is already set, so a run can also resume from a dev jump-in (?dev=world&play=1&flags=…):

if (!flag("got_seed")) {
  await nav("fennimore_house");
  await talkTo("fennimore");
  await expectFlag("fennimore gives the seed", "got_seed");
}

The battle driver

Battles are fought by the same menus a player uses. When the battle opens its FIGHT / BAG / QUICKENED / RUN menu, a hook decides the target and advance presses arrows until the cursor is there. The choices come from e2e/battle-driver.ts:

  • strongestMove scores every legal move with the game's own calcDamage (type chart, STAB, weather, stages) at a fixed roll, so it never consumes a random number and cannot change the battle's outcome by thinking.
  • healingItem uses medicine only when HP is below a third, and only medicine the story already gave: the driver never creates items.

To keep the story moving, the run adds an over-levelled helper (level 48 by default, flagged e2e) after the starter and heals it between beats. The playthrough tests the story flow, not the difficulty; the balance bands test difficulty.

export class ProgressWatchdog {
  private signature: string | undefined;
  private changedAt = 0;
  private reported = false;

  sample(signature: string, wallTime: number): boolean {
    if (signature !== this.signature) {
      this.signature = signature;
      this.changedAt = wallTime;
      this.reported = false;
    }
    if (!this.reported && wallTime - this.changedAt >= NO_PROGRESS_MS) {
      this.reported = true;
      return true;
    }
    return false;
  }
}

The signature deliberately leaves out things that tick even when the game is stuck (blinking cursors, idle animation clocks). It includes a counter that goes up each time a tracked operation (a say, a menu, a jingle, a cry) starts or finishes, so a long jingle is progress but a jingle that never ends is not.

The report

The runner writes e2e/last-report.json (git-ignored) on success, failure, timeout and Ctrl-C alike. It holds beats (name, ok, time, map, position, new flags, note, screenshot as a data URL), issues, every line of dialogue in texts, every battles request and outcome, frame-time stats, and runner (target production or dev, speed, seed, elapsed time, runner issues). The exit code is 0 only when all of this holds:

const failures = report.beats.filter((b) => !b.ok).length;
if (report.beats.length !== 217) runnerIssues.push(`Expected all 217 beats; received ${report.beats.length}`);
process.exitCode = failures === 0 && report.issues.length === 0 && runnerIssues.length === 0 ? 0 : 1;
In a headed run, open the browser console: __e2e.summary() prints the beats and issues without images, and __e2e.sheet() overlays a contact sheet of the beat screenshots (click to close).
Advanced: flakiness and how to triage it

The playthrough is deterministic in its choices but not in its timing. Its waits and its 12-second watchdog are wall-clock time, because Web Audio (cries and jingles) always plays on the real clock whatever ?speed says. Two known causes make a correct build fail:

  • Machine load. On a busy machine, a long boss fight or a map load can starve the page long enough for the watchdog or the overall timeout to fire. A stall seen once at a late leader was load; the rerun passed.
  • A stalled audio clock hangs jingles. playJingle and playCry resolve only when the audio engine's scheduler sees AudioContext.currentTime pass the end of the song. If the headless browser's audio context reports running but its clock never advances (seen on a Mac whose audio service was stuck), the promise never resolves, the heal or "caught" jingle never ends, and the watchdog reports soft-lock? right after it. The detector test pins this on purpose: "An audio promise that never resolves still reports a lock." Restarting the machine's audio service fixes it; until then, rely on CI.
flowchart TB
  F["e2e failed"] --> S{"Same seed, rerun: fails at the same beat?"}
  S -- no --> LOAD["Timing: check machine load, rerun on CI"]
  S -- yes --> J{"Stalled right after a jingle or cry, locally only?"}
  J -- yes --> AUD["Audio clock stuck: trust CI, restart the audio service"]

The beat count 217 is written in several places: e2e/run.mjs, e2e/runner.test.ts, the workflow step name, AGENTS.md and the README. Adding or removing a beat means updating all of them in the same commit, or the runner reports "Expected all 217 beats".

Before adding a sleep to make a beat pass, find what the beat is waiting for and wait on that state (waitFor, advance(…, done)). Fixed sleeps are the main source of load-sensitivity.

  X -- no --> OK["release-check: OK"]
walk("src", (path) => {
  try {
    read(path).split("\n").forEach((line, index) => {
      for (const marker of ["TODO(text)", "allowTodo"]) {
        let column = line.indexOf(marker);
        while (column !== -1) {
          offenders.push(`${path}:${index + 1}:${column + 1}: contains ${marker}`);
          column = line.indexOf(marker, column + marker.length);
        }
      }
    });
  } catch (error) {
    offenders.push(`${path}: cannot check source: ${error.message}`);
  }
});

Only src/ and public/art/ are scanned, so the e2e code in e2e/ may mention allowTodo. Each offender is printed with file, line and column. In CI it runs after the tests and before the build (see the pipeline).

Advanced: why the word allowTodo is banned in src/

The e2e tolerance for placeholder dialogue is switched on by the URL parameter allowTodo. Banning the word in src/ means production code can never grow a code path that reads it, so the tolerance cannot leak out of the test harness. The scan also fails on anything it cannot read (a symlink, unparsable JSON), because a check that skips what it does not understand is a check that can be bypassed.

release-check.test.ts spawns the real script with node in a temporary directory, so the test covers the CLI's exit code and output, not just its helpers.
