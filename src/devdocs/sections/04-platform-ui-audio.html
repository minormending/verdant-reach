Platform, UI and audio

Three layers sit between the engine and the player. src/platform is the page around the canvas: how big it is, the touch controls, fullscreen, pausing, the error card and the loading screen. src/ui is everything drawn with the bitmap font: the text box, menus, the naming screen, the title and the NEW GAME intro. src/audio is a small chip synthesiser that plays every note of music and every sound effect live.

The page shell

createShell(canvas, onInteract) builds the DOM around the canvas: a #vr-bezel frame, a hidden #vr-safe probe whose padding is env(safe-area-inset-*) (so the layout can read notch insets), the fullscreen button #vr-fs, and the touch controls. Every resize, orientation change, fullscreen change and devicePixelRatio change re-runs one apply() that computes a layout and positions everything. Only main.ts imports the platform layer, through src/platform/index.ts.

  ev["resize, orientationchange, fullscreenchange, DPR change, touch mode change"] --> apply["apply()"]
  apply --> safe["read safe-area insets from #vr-safe"]
  safe --> layout["computeLayout: vw, vh, dpr, touch, safe"]
  layout --> canvas["canvas left/top/width/height"]

  layout --> dataset["html data-layout: desktop, portrait or landscape"]

Fullscreen toggles from the button or the F key (not with a modifier, not on auto-repeat), using the standard API with webkit fallbacks and navigationUI: "hide". The button is hidden where fullscreen isn't supported, and a denied request is swallowed.

platformFlags() decides two things from the URL: the shell is off for the ?dev=world overview (a plain document), and pause-on-blur is off under ?timer, ?nopause and ?e2e.

Layout and integer scaling

The 160×144 canvas is scaled by a whole number so each game pixel is a perfect square. The subtle part is which pixels: the scale is counted in device pixels, not CSS pixels. At a devicePixelRatio of 1.25, a CSS scale of 3 would be 3.75 device pixels per game pixel, and rows would alternate between 3 and 4 pixels tall. layout.ts is pure maths (no DOM), so it is unit-tested: 

/** Largest integer device-pixel scale that fits the area (at least 1). */
export function integerScale(availW: number, availH: number, dpr: number): number {
  const s = Math.floor(Math.min((availW * dpr) / GB_W, (availH * dpr) / GB_H) + 1e-6);
  return Math.max(1, s);
}

/** Snap a CSS coordinate to the device-pixel grid. */
export const snap = (v: number, dpr: number) => Math.round(v * dpr) / dpr;

/** Centre a scaled screen inside an area, snapped to device pixels. */
export function placeScreen(area: Rect, scale: number, dpr: number): Rect {
  const w = (GB_W * scale) / dpr;
  const h = (GB_H * scale) / dpr;
  return { x: snap(area.x + (area.w - w) / 2, dpr), y: snap(area.y + (area.h - h) / 2, dpr), w, h };
}

Advanced: layout invariants and a duplicate resize path
  • Controls never cover the screen. layout.test.ts uses overlaps() to check this across viewport sizes; run it after any change to the constants.
  • The 1e-6 epsilon stops floating-point error (for example 480 * 1.5 / 160) from dropping a whole scale step.
  • Landscape on tablets (short side at least 600px) keeps the control unit at least 4, so buttons never shrink below thumb size to win one screen scale step.
  • Two resize handlers. createCanvas in engine/core.ts also listens to resize and sets a CSS-pixel integer scale. With the shell on, the shell's handler is registered later and overrides it on every resize; with the shell off (the world overview), the engine's simpler fit is what you get. If you change one, check the other.
  • DPR watching uses a matchMedia("(resolution: …dppx)") query that re-arms itself after each change, because there is no devicepixelratiochange event (moving a window between monitors, or browser zoom).

Touch controls

On touch devices, touch.ts draws a D-pad, A and B, and START and SELECT pills as small pixel-art canvases. Each control synthesises the same KeyboardEvents the keyboard does, so the engine sees a key press and cannot tell a tap from a key: 

export const TOUCH_KEYS = {
  up: "ArrowUp", down: "ArrowDown", left: "ArrowLeft", right: "ArrowRight",
  a: "KeyZ", b: "KeyX", start: "Enter", select: "ShiftLeft",
} as const;

export function sendKey(code: string, type: "keydown" | "keyup") {
  dispatchEvent(new KeyboardEvent(type, { code, bubbles: true, cancelable: true }));
}

  participant D as D-pad element

  • The D-pad takes one pointer and lets the thumb slide between directions. The direction is the dominant axis from the pad's centre, with a dead zone of 12% of its size.
  • Buttons count pointers, so two fingers on A send one keydown and one keyup.
  • When the pad shows: isTouchDevice() (?touch=1|0 wins, else a coarse pointer, or touch points with no hover). A first touchstart on a hybrid laptop brings it up; a trusted key press from a real keyboard hides it until the next tap.
Advanced: synthetic events and stuck keys
  • Synthetic events are untrusted (isTrusted === false). That is how the shell tells a real keyboard from the touch pad, and also why a tap cannot unlock audio through the key path: the controls call onInteract() (the audio unlock) on pointerdown, and main.ts calls it again on window pointerup/touchend, which is when mobile browsers actually grant permission.
  • Hiding releases everything. setVisible(false) runs each control's release function (sending keyups), so switching to a keyboard mid-press can't leave a direction held. releaseAll() exists for the same purpose but nothing outside touch.ts calls it today; on window blur the engine clears its own key set instead.
  • Pointer capture keeps pointermove/pointerup coming to the control even when the finger leaves it; pointercancel is handled like pointerup.
  • Gestures are suppressed: controls set touch-action: none, contextmenu is prevented, and the page disables selection and the tap highlight in index.html.

Pause on focus loss

When the window blurs or the tab hides, createPause pushes a transparent PAUSED scene. Because the loop only updates the top scene, everything underneath stops; audio is suspended (setAudioSuspended) and play time stops accruing. Any button, or a tap on the canvas, resumes. 

stateDiagram-v2
  [*] --> Running
  Running --> Paused: blur or visibilitychange hidden (if booted and no error card)
  state Paused {
    [*] --> Disarmed
    Disarmed --> Armed: all buttons released and more than 6 frames
    Armed --> [*]: any button pressed
  }
  Paused --> Running: resume()
  Paused --> Running: pointerdown on canvas
Advanced: why "armed", and removing a scene that isn't on top
  • The resume press must not act in the game. The overlay waits until every button is released (and 6 frames have passed) before it listens, and the press that resumes is consumed by the overlay's own update, so it can't also confirm a menu underneath.
  • Something may push above the overlay (an async flow finishing while paused). resume() therefore splices its scene out of scenes.all() wherever it is, and falls back to pop() only if it is on top of a stack without all().
  • Disabled for automation: hidden test panes (?timer), ?nopause and e2e runs must never pause themselves.

The error screen

installErrorScreen logs every uncaught error and unhandled rejection, but only shows the "Something wilted… Let's replant it." card when the game has actually stopped. A glitch in a timer shouldn't end a session that could carry on. 

flowchart TB
  err["window error or unhandledrejection"] --> benign{"browser noise? (ResizeObserver loop, Script error, AbortError, interrupted play())"}
  benign -->|yes| ignore["ignore"]
  benign -->|no| log["console.error"] --> wait["remember ticks, wait 600 ms"]
  wait --> hidden{"tab hidden and not ?timer?"}
  hidden -->|yes| vis["re-check when visible again"]
  hidden -->|no| moved{"ticks advanced?"}
  moved -->|yes| carry["loop alive: keep playing"]
  moved -->|no| card["draw the card: Z, Space, J, Enter or a tap reloads"]
  boot["boot() catch"] --> fatal["errors.fatal(err)"] --> card

The card is drawn straight onto the canvas with a short upper-case error code in the corner for bug reports. If even drawing fails, a plain DOM fallback (.vr-fallback-error) appears. Reload listeners are attached after 400 ms so the key that caused the crash doesn't immediately reload.

Advanced: liveness, not exceptions, decides
  • Why ticks: an exception inside a scene's update kills the frame callback (nothing reschedules it). Errors in promises or timers don't. Comparing the tick count before and after 600 ms is a cheap, reliable "is the loop dead?" test.
  • Hidden tabs stop requestAnimationFrame, so a still tick count proves nothing there; the check is deferred until the tab is visible (except under ?timer, where the loop runs on timeouts).
  • A live loop after a boot failure: onShow in main.ts stops the music, clears the stack and pushes a scene whose draw repaints the card, so the loop doesn't paint over it.

The loading screen

createLoadingScene draws the logo (or "VERDANT REACH" in the font until the logo loads) over a night-green field, and a vine that grows along the progress bar, putting out a leaf every 9 pixels. progress(done, total) sets a target and the vine eases towards it by a quarter of the gap each frame. finish() resolves only once the vine is full, plus a 180 ms hold, so a fast load never flashes. Boot loads title_logo first so the screen can show it.

The bitmap font

All text is drawn with an 8×8 bitmap font in the style of Gold, Silver and Crystal (2px vertical strokes, 7px cap height, one blank column for spacing). The glyphs are authored in src/ui/font.ts as ASCII art, eight per block: 

const BLOCKS: { chars: string; rows: string[] }[] = [
  {
    chars: "ABCDEFGH",
    rows: [
      "..###... ######.. ..####.. #####... #######. #######. ..####.. ##...##.",
      ".##.##.. ##...##. .##..##. ##..##.. ##...... ##...... .##..##. ##...##.",
      // …
    ],
  },
  // …
  • 108 glyphs: A–Z, a–z, 0–9, punctuation, and symbols such as ♪ é … × ♂ ♀ arrows, ▶ ▷ ▼ ▲ ◀, — @ · ♥ ✓.
  • An atlas per colour: glyphAtlas(color) bakes every glyph into one canvas the first time a colour is used; drawBitmapText then blits 8×8 cells (optionally at an integer scale).
  • Fallbacks: ALIASES map curly quotes, en dash, non-breaking space, É, ▸/► and ⋯ to glyphs that exist; anything else draws ? and logs once.
  • Pure helpers (measureText, wrapText, paragraphs, formatText) never touch the DOM, so they run under Vitest. Text is measured in code points (Array.from), so é or ♪ is one column.

The text box and its paging rules

TEXTBOX in constants.ts is { x: 0, y: 96, w: 160, h: 48, cols: 18, lines: 2 }: a full-width box at the bottom showing 18 columns × 2 lines. Game code calls await ctx.ui.say(text); the TextBox class in src/ui/kit.ts does the rest, the way Crystal does it:

  1. Formatting: {PLAYER}, <PLAYER> or [PLAYER] become the player's name ("YOU" if empty), and the same for RIVAL (default "BRAM"). opts.speaker prefixes "SPEAKER: ".
  2. Pages: paragraphs() splits on a blank line ("\n\n") or "\f". Each paragraph starts in a fresh, empty box.
  3. Lines: inside a paragraph, words wrap at 18 columns, "\n" forces a break, and a word longer than 18 is split.
  4. Typing: characters appear at the text-speed option (slow ¼, mid ½, fast 1 character per frame); holding A or B types 2 per frame. A blip SFX plays per visible character, at most every 4 frames.
  5. Scrolling: when line 2 fills and the paragraph continues, ▼ bobs; A or B scrolls the box up one line over 4 frames and typing continues on the bottom line.
  6. End: on the last page the box waits for A or B, then say resolves. autoClose closes 40 frames after the text finishes instead.
export type TextSpeed = "slow" | "mid" | "fast";
/** Characters revealed per frame (fractions accumulate). */
const SPEED: Record<TextSpeed, number> = { slow: 1 / 4, mid: 1 / 2, fast: 1 };

Advanced: text-fit validation and the hand-off to menus
  • Fit is checked at test time. src/world/validate.ts wraps every script line and fails when a word can't fit 18 columns. Note that it has its own wrapText (string .length, no long-word splitting) rather than the font's; the two agree for ASCII but can disagree for multi-code-unit characters. Keep them in step if you change wrapping rules.
  • The lingering box. After say finishes, the kit remembers the visible two lines. A choose() without its own prompt, called within 80 ms, draws them under the menu, so "Will you help?" stays on screen while YES/NO opens. The window is measured in wall-clock time (performance.now()), not frames.
  • Pressing A to advance while holding it also counts as "hold to type fast" on the next page, which matches how players mash through text.
  • Empty text becomes one empty page, so say("") still waits for A instead of resolving instantly.

The chip synth

src/audio/engine.ts is a WebAudio take on the Game Boy's sound chip. The Chip has the same four voices: two pulse channels (12.5/25/50/75% duty, built as band-limited PeriodicWaves), a wave channel (a triangle-ish bass) and an LFSR noise channel (white or metallic, plus kick/snare/hat/crash drums). Notes are scheduled slightly ahead on the audio clock by a 25 ms timer (0.18 s lookahead, 1.5 s when the tab is hidden and timers are throttled), so timing never depends on the frame rate.

  sfxP["SFX Player"] --> effectBus["effectBus x3.0"] --> sfxBus["sfxBus (sound volume)"]

The audio service: music, jingles, SFX and cries

createAudio() in src/audio/index.ts implements AudioService. It is a full state machine even when silent: playMusic records the current track whether or not sound is available, so the right music starts the moment audio unlocks.

  • playMusic(id) is a no-op when that track is already playing, so maps can call it freely on entry. It also picks the ambience bed for the track.
  • playJingle(id) stops the music, remembers its position, plays the jingle and resumes the music from that position (with a 0.25 s fade-in) when the last overlapping jingle ends.
  • playCry(species) ducks the music: it lowers duckGain to 0.45 while the cry plays and restores it after. Ducks are counted, so overlapping cries don't restore early.
  • Silence never blocks. When the context isn't running, playSfx does nothing and playJingle/playCry resolve immediately, so scripts that await a jingle never hang without sound.
  • The mix (mix.ts) was set by rendering everything offline (e2e/audiomix.ts) and comparing loudness: per-category trims, per-track MUSIC_TRIM, per-effect SFX_TRIM.
Advanced: scheduling, buses and adding sounds
  • Lookahead scheduling means a note is committed up to 0.18 s before it sounds; stop(fade) cuts the live sources and fades the player's own gain, so stops are click-free but not sample-exact. Voices start at gain 0 because a default-1 GainNode leaked one full-level sample before the envelope (an audible click on about 1 kick in 8).
  • Jingles ride the music bus so they follow the music volume; cries and ambience ride the SFX bus. Ducking sits on the music path only.
  • Default volumes differ by layer. DEFAULT_VOLUME in mix.ts is music 0.8, SFX 0.9, but the options screen's defaults are 8 and 8 (out of 10) and are applied at startup, so a fresh browser plays SFX at 0.8.
  • Adding a sound: add the id to MUSIC, SFX or JINGLES in src/contracts/ids.ts (a contract change), then its definition; the Record<MusicId, …> types make a missing definition a compile error. The tests in audio.test.ts check that every music track parses, loops last 30–90 s and every melody bar is exactly one bar long. Try it in ?dev=audio, and re-measure the mix if it is long or loud.

The unlock rule, and why controllers can't unlock audio

Browsers' autoplay policy only lets a page start sound after a user activation: a trusted key press, click, or the end of a tap. So the audio service creates its AudioContext lazily, inside unlock(), which the game calls from several places: 

sequenceDiagram
  participant U as player
  participant In as engine input
  participant Sh as touch controls
  participant W as window listeners
  participant Au as audio.unlock()
  U->>In: mapped keydown (not auto-repeat)
  In->>Au: onPress() on every new key press
  U->>Sh: pointerdown on a control
  Sh->>Au: onInteract()
  U->>W: pointerup or touchend anywhere
  W->>Au: unlock()
  U->>In: gamepad button press
  In->>Au: onPress() on every new pad press
  Au->>Au: already running? return at once
  Au->>Au: create Chip(new AudioContext) once, apply volumes
  Au->>Au: ctx.resume(), then start the current music and bed

Why a controller alone can't do it: a Gamepad API button press is not a user-activation event in browsers, so an AudioContext created or resumed from it stays suspended. The engine still calls onPress() on every new pad press, as it does on every new key press, so once the player has pressed a key or tapped once, the next pad press succeeds. A pad-only player hears nothing until then. Asking again is cheap: unlock() returns at once when the context is already "running".

Touch is the other trap: mobile browsers grant permission on pointerup/touchend, not pointerdown, which is why main.ts adds those two window listeners:

    // Touch only grants audio permission on pointerup/touchend, not pointerdown.
    const unlock = () => game.audio.unlock();
    addEventListener("pointerup", unlock);
    addEventListener("touchend", unlock);
Advanced: suspend, resume and the Escape key
  • Pause wins. setAudioSuspended(audio, true) suspends the context; while suspended, unlock() creates the chip if needed but does not resume it, so a tap during the PAUSED overlay can't start music under it.
  • After resume() the service restarts the current music from the saved position and the ambience bed if it had none, which covers music requested while locked.
  • Every press retries. The HTML spec excludes the Escape key from user activation, and Escape is mapped to B, so a player's first key may create a context that stays suspended. That is why createInput calls onPress on every new mapped keydown (auto-repeat excluded), and the window listeners fire on every pointerup/touchend: the next real gesture resumes it. Music can't start twice: each resolved resume() starts the current track only if none is playing (!music), and once running, unlock() does nothing.
  • Without WebAudio (tests, very old browsers) unlock() returns early and the service stays a silent state machine; nothing else changes.
